# CLAUDE.md — cred_risk (БРМ, АО «Евразийский банк»)

Репозиторий рабочих контуров БРМ: сверка DWH, лимиты, риск-аппетит, классификация документов.
Один автор (Мирас), внешний ревьюер по одному контуру (Сайлау), **CI нет** — ни один PR
не проверяется автоматически. Всё, что ниже, написано под это, а не под общие практики.

Контурные CLAUDE.md имеют приоритет над корневым в своей папке.

## 1. Ветвление

### Почему правила именно такие

Имя ветки задаёт харнесс при старте сессии (`claude/<slug>-<хеш>`), а не автор. Слаг привязан
к первой задаче сессии и дальше не меняется, поэтому **имя ветки не описывает её содержимое**
и описывать не будет. Факты по репозиторию на 18.08.2026: ветка
`claude/database-table-analysis-wxxgtv` за месяц провела 9 PR по трём несвязанным темам —
инвентаризация DWH, отзыв находки по grain, лимиты НЗ/СП. Ветка
`claude/cred-risk-topic-classifier-1cjbtk` — 8 PR, от классификатора документов до Phase C/D.

Отсюда правила не про имена, а про поведение: **носителем смысла является PR и путь
`docs/analysis/<контур>/`, а не имя ветки.**

### Правила

**Б1. Один PR — один контур.** Все файлы PR лежат под одним `docs/analysis/<контур>/`
(либо под одним каталогом верхнего уровня: `sql/`, `topic_classifier/`, `notebooks/`).
Проверка перед пушем:

```
git diff --name-only origin/main...HEAD | cut -d/ -f1-3 | sort -u
```

Больше одной строки — PR надо разделить. Смешанный PR нельзя ни отревьюить, ни откатить.

**Б2. Ветка после слияния мертва.** Как только PR смёрджен, ветка не продолжается.
Следующая задача начинается с

```
git fetch origin main && git checkout -B <та-же-ветка> origin/main
```

Продолжение работы поверх смёрдженной истории — источник PR, диффы которых нельзя прочитать.
Если на ветке остались **не** слитые коммиты — их сначала перебазировать на новый main,
а не сбрасывать.

**Б3. Ветка живёт до 7 дней и до ~20 коммитов.** Больше — либо приземлять, либо разделять.
Наглядный контрпример в самом репозитории: `risk-dwh-bi-canvas` — 70 коммитов, +16 141 строка,
34 файла, открыта с 30.07, отстала от main на 20 коммитов. Такой PR физически неревьюабелен,
и каждый день его существования увеличивает стоимость слияния.

**Б4. Заблокированный PR синхронизируется с main еженедельно.** Если PR ждёт человека,
это не повод давать ему протухать: `Update branch` на GitHub либо merge main в ветку.
Конфликты дешевле разбирать по одному, чем все сразу через месяц.

**Б5. Кто мёрджит.** GitHub **не разрешает автору апрувить собственный PR** — попытка
возвращает `Can not approve your own pull request`. Поэтому для одиночной работы схема такая:
draft → самопроверка → снять draft → merge. Ждать апрува, которого не может быть, нельзя.

**Исключение, которое важнее правила:** если в PR назначен живой ревьюер (`requested_reviewers`)
или в теле PR есть незакрытые пункты, отмеченные его именем, — **PR не мёрджится без него**,
сколько бы он ни висел. Пример: PR #19 ждёт прогон №2 от Сайлау; слить его в одиночку —
значит внести в main 71 SQL-проверку, из которых шесть уже один раз оказались багами скрипта,
а не дефектами марта.

**Б6. Метод слияния — merge commit** (не squash, не rebase). История PR в этом репозитории
сама по себе документ: по ней видно, где находка была отозвана (PR #14 → #15).

**Б7. Ветки, слитые полностью, удаляются.** Проверка списка мёртвых веток:

```
git fetch --prune origin
git for-each-ref --format='%(refname:short)' refs/remotes/origin | while read b; do
  if [ "$b" != origin/main ] && [ "$(git rev-list --count origin/main..$b)" = 0 ]; then
    echo "мертва: $b"
  fi
done
```

### Что НЕ является правилом

Здесь нет develop/release/hotfix, нет запрета на прямой коммит в ветку, нет требования
линейной истории и нет обязательного ревью. Один автор без CI — вводить это значит
имитировать процесс, а не иметь его.

## 2. Конфиденциальность — жёстко

**Не попадает в репозиторий ни при каких условиях:**

- Исходные ВНД Банка (Стратегия, Политика, Методика, приложения, протоколы) — промаркированы
  «ВНУТРЕННЯЯ ИНФОРМАЦИЯ» / «конфиденциально». В репозитории только **результаты анализа
  со ссылками на пункты**.
- PII: ИИН, ФИО, номера договоров, IBAN, телефоны. Только агрегаты.
- Выгрузки из промышленных систем и оперативные файлы подразделений. Код сбора — да,
  собранные данные — нет. Ноутбуки коммитятся **без сохранённых выводов**.
- Учётные данные, строки подключения, содержимое `.env`.

Публичные НПА (постановления АРРФР/НБ РК) цитировать можно, но с указанием редакции
и рег. номера.

Перед коммитом бинарников и .docx — открыть и посмотреть, что внутри. `.docx` не диффится,
поэтому попавший в него лишний лист незаметен в PR.

## 4. Правила SQL (действуют во всём репозитории)

- **Read-only.** Только SELECT. Запрещены INSERT/UPDATE/DELETE/MERGE/DROP/ALTER постоянных
  объектов. Только `#temp`, имена — с префиксом файла.
- **MAXDOP 1** на тяжёлых запросах.
- **PII не выводить.** Только агрегаты; худшие случаи — бакетами величины, не идентификаторами.
- **Только трёхчастные имена:** `[Dictionaries].[risk_analytics].[X]`.
- **Имена колонок — только из живого аудита** (`INFORMATION_SCHEMA`), не из BI-канваса
  и не из памяти. Имя колонки ≠ семантика.
- `CROSS APPLY (VALUES …)` ставить **после** фильтра.
- Сначала агрегат, потом детализация. Не `SELECT *`, не `FORMAT` на больших выборках.

Развёрнутые правила движка, порядок проверки и антипаттерны —
в `docs/analysis/risk_dwh_reconciliation/CLAUDE.md`.

находку отзывать явно, отдельным коммитом (образец — PR #15).

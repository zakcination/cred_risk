# Протокол офиса агентов

Слой поверх `docs/pm/CONFIG.md`: там задано, что такое задача (issue) и контур (метка
`contour:*`); здесь — кто её ведёт, как отчитывается, где это хранится и в каком ритме.

**Редакция 2 от 09.10.2026.** Принята по исследованию `RESEARCH_2026-10.md` (в этой папке).
Редакция 1 (07.10.2026) строилась на «оркестратор + 3 долгоживущих агента» и отменена
явно, а не задним числом — что именно и почему, в §9. Реквизиты сессий и routines —
`REGISTRY.md`, гипотезы, на которых держится редакция, — `HYPOTHESES.md`.

## 1. Главный принцип

**Агент — исполнитель одной issue, а не сотрудник с памятью.** Память офиса — репозиторий,
issue, протоколы хода и `HANDOFF.md`; сотрудники — Мирас и эти файлы. Основание:
длинный контекст деградирует задолго до заполнения окна [измерено: NoLiMa, Chroma],
LLM-менеджер не добавляет качества при росте токенов в ~3,9 раза [измерено:
arXiv 2512.08296, MA-Gym], пересылка через посредника — треть отказов мультиагентных
систем [измерено: MAST]. Ссылки — в `RESEARCH_2026-10.md`.

## 2. Роли

| Роль | Кто | Что делает | Чего не делает |
|---|---|---|---|
| **Диспетчер** | Мирас | режет работу на issue (≲ 1 ч экспертного труда, проверяемый выход), согласует шаги 1–3 §6, мёрджит | — |
| **Секретарь** | routine «утренняя доска» + пятничная (`REGISTRY.md`) | переписывает тело «Доски агентов» (#161), собирает «Ждёт решения» одним комментарием | не формулирует задачи, не пересказывает их сессиям, не выбирает метрику, не мёрджит |
| **Сессия на issue** | новая облачная сессия Claude Code | одна issue от старта до протокола и draft PR | не берёт вторую issue, не живёт дольше issue |
| **ПК-сессия** | Remote Control на рабочем ПК (`REGISTRY.md`) | единственная, кто касается данных Банка: прогоны скриптов, выгрузки, `R:\` | наружу — только агрегаты и контрольные итоги (§2, §4 корневого `CLAUDE.md`) |
| **Ревьюер** | свежая сессия, только для PR, меняющих находки | пересчёт и сверка с независимым источником | не оценивает «убедительность текста» |

Поручение сессии — **текст issue**, который она читает сама. Пересказ поручения через
`send_message` не используется: это и есть «испорченный телефон» (MAST).

## 3. Жизненный цикл issue

1. **Мирас** заводит issue: контур, вопрос, ожидаемый проверяемый выход. Метка `contour:*`.
2. **Сессия** стартует по ритуалу §4, пишет шаги 1–3 §6 (подход, план данных, план
   обработки) **комментарием в issue** и останавливается — статус «ждёт автора».
3. **Мирас** согласует или правит план комментарием. Без этого комментария первый коммит
   скрипта запрещён.
4. **Сессия** пишет скрипт/текст → draft PR (`Closes #N`) → протокол хода §5.
5. Если нужны данные — **ПК-сессия** прогоняет утверждённый скрипт; в issue — агрегаты.
6. **Ревьюер** — только если PR меняет статус находки, гипотезы или вопроса (§7).
7. **Мирас** снимает draft и мёрджит (Б5). Сессия закрывается (§6).

## 4. Ритуал старта сессии

Первое сообщение любой сессии на issue:

```
Ты ведёшь issue #<N> в zakcination/cred_risk по docs/pm/agents/PROTOCOL.md.
1. Прочитай issue #<N> и все комментарии, docs/analysis/<контур>/HANDOFF.md (если есть),
   CLAUDE.md контура, git log по контуру за 2 недели.
2. Проверь, согласован ли план §6 комментарием Мираса. Нет — напиши шаги 1–3 и остановись.
3. Работай только в контуре <контур> (Б1). Чужой контур — новая issue, не правка.
4. В конце каждого хода — протокол §5 комментарием в issue.
5. Перед закрытием — дельта в HANDOFF.md (§6), чистое состояние ветки.
```

## 5. Протокол хода

Комментарий в issue в конце каждого хода:

```
[сессия] #<issue> · <контур> · <дата>
Статус: в работе | ждёт автора | готово к ревью | заблокировано
Сделано: <1–3 строки, ссылки на коммит/PR>
Доказано на данных: <…или «—»>
Из документа: <…или «—»>
Гипотезы: <номера из реестра контура или «—»>
Ждёт решения Мираса: <пронумеровано: вопрос + варианты + источник довода>
Проверяемое доказательство: <дифф с прошлым прогоном / контрольные суммы / дословный пункт>
Следующий шаг: <одна строка>
Контекст: <used_tokens / max_tokens>
```

«Ждёт решения» — единственное, что секретарь выносит Мирасу. На согласование идёт
**проверяемое доказательство**, а не готовый нарратив: автоматизационный уклон сильнее
всего действует на убедительный готовый результат [измерено: EDPS TechDispatch 2/2025].

## 6. Когда сессия закрывается

По **событию**, а не по проценту окна:
- issue закрыта;
- работа ушла в другой контур;
- две попытки исправления подряд не удались [вендор: Claude Code best practices].

Страховочный предел: контекст **> 25–30 % окна** → передать дела, даже если issue не
закрыта (гипотеза Г-3).

**Передача дел** — `docs/analysis/<контур>/HANDOFF.md` по `HANDOFF_TEMPLATE.md`, **только
дописыванием**: новая датированная дельта сверху, прежние не переписываются.
Основание — ACE: переписывание накопленного контекста ведёт к его «схлопыванию»
[измерено: arXiv 2510.04618]; то же правило §5 корневого `CLAUDE.md` для отзыва находок.

## 7. Проверка

Ревью — **пересчётом и сверкой**, а не перечитыванием той же моделью: самопроверка без
внешней опоры не улучшает рассуждение и скатывается в одобрение [измерено:
arXiv 2310.01798, 2606.28438]. Ревьюер в свежей сессии:
- сверяет контрольные итоги с независимым источником (`FINDINGS.md` сверки, `CL_PORTFOLIO` ↔ mart, факт ↔ модель);
- сверяет цитаты пунктов с `npa_registry/CITED.md`;
- проверяет, что SQL read-only (§4 корневого `CLAUDE.md`);
- не даёт оценку «насколько убедительно написано».

| 08:30–09:15 | Мирас | блок решений: планы §6, ответы, нарезка новых issue; проверить, что ПК-сессия на связи |
| 09:15–12:00 | 2–3 облачные сессии | по одной на согласованную issue, каждая в своём контуре; субагенты — только read-only разведка |
| 12:00–12:30 | Мирас + ПК-сессия | прогон утверждённых скриптов; в issue — агрегаты и контрольные итоги |
| 12:30–13:00 | Мирас | пакетный разбор PR по доказательствам; ревьюер — только для PR, меняющих находки |
| 14:00–17:00 | вторая волна | то же по новым решениям; сессии закрытых issue завершаются |
| 17:30 | каждая сессия | дельта `HANDOFF.md`, финальный протокол, чистая ветка |
| пт 15:52 | routine + Мирас | Б4, Б7, метрики недели, сверка гипотез `HYPOTHESES.md`, чистка CLAUDE.md по наблюдённым сбоям |

**Одновременно — не больше 2–3 сессий, каждая в своём контуре.** Предел задаётся не числом
агентов, а числом решений, которые Мирас успевает обдумать (Г-1).

**Метрики** (из GitHub, без ручного учёта; считает пятничная routine): медиана issue →
слияние; доля планов §6, принятых без переделки; PR с отзывом находки в 30 дней; решений,
вынесенных автору в день. Причина объективных метрик: в РКИ METR разработчики с ИИ были
на 19 % медленнее, считая себя на ~20 % быстрее [измерено].

## 9. Что отменено из редакции 1 и почему

| Было (07.10.2026) | Стало | Причина |
|---|---|---|
| 3 долгоживущих агента `agent:<N>` | сессия на issue | деградация длинного контекста; два агента были на ~70 % окна |
| оркестратор пересказывает поручения `send_message` | поручение = текст issue; секретарь только сводит | MA-Gym, MAST |
| агент → оркестратор через `fire_trigger` | протокол хода в issue читает секретарь | один канал вместо двух; входящий триггер не нужен |
| передача дел при > 70 % окна | закрытие по событию + предел 25–30 % (Г-3) | Claude Code best practices; NoLiMa |
| метка `agent:<N>` | не используется | исполнитель не переживает issue |

Сохранено без изменений: issue как очередь, протокол хода с разделением «доказано / из
документа / гипотеза», §6 «сначала согласование» (усилено: план — комментарием до первого
коммита), «один контур — одна сессия», «оркестратор не мёрджит», режим `auto`,
сырые данные — только на ПК.

## 10. Привязка к аккаунту

Протокол не зависит от аккаунта Claude; от аккаунта зависят только реквизиты в
`REGISTRY.md` (ПК-сессия, routines). Сессии и routines между аккаунтами не переносятся,
сессия одного аккаунта не управляет сессиями другого — при смене аккаунта всё
пересоздаётся одновременно от issue и `HANDOFF.md`.

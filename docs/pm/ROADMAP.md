# Профиль рисков банка — дорожная карта

> Продуктовый слой над контурами БРМ. Живой документ: обновляется дельтами, не переписывается.
> Состояние на **01.09.2026**.

Репозиторий — база знаний по кредитному риску: ход работы и локальная история, сохранённые
так, чтобы их можно было передать. Этот файл — единственное место, где восемь контуров видны
как одна работа, с датами и состоянием. GitHub (milestones + issues) — оперативный срез
того же самого; здесь — устойчивая запись.

## 1. Что является продуктом

Фразы «профиль рисков банка» в репозитории нет. Есть её реализация: **`risk_showcase` —
витрина риск-метрик.** Движок над 50 метриками на 4 «полочках», по одной полочке на
нормативный документ; считает зону, утилизацию, скорость, время до пробоя, σ-расстояние и
счётчики длительности. Существует, чтобы закрывать графы 6, 9 и 10 таблицы 2 структуры
отчёта ВПОДК.

**Витрина — поверхность продукта; остальные семь контуров — доказательная база под ней.**
Движок функционально готов и пуст: `--selftest` проходит, `data/observations.csv` в gitignore.

### Спина

**ДС3 (доля Stage 3) и КПП (покрытие провизиями)** — одновременно:

| Где | Роль |
|---|---|
| `dpd15_cure` | выход расчёта |
| `bank_recovery` | триггер режимов № 119 |
| `npl_limits` | числитель лимита 98-3 |
| `risk_appetite` | **отсутствующая** метрика — предложение RA-08 добавить НЗ/СП в аппетит |
| `risk_showcase` | полочка |
| Stage-3 | периметр — определение НЗ по № 85 опирается на критерии обесценения № 61 |

Это и есть причина, по которой восемь контуров — один продукт, а не восемь тем.

## 4. Как это отслеживается

Четыре уровня, каждый ложится на уже существующую поверхность. Новых сущностей нет:

```
Продукт      Профиль рисков банка / витрина     docs/pm/ROADMAP.md
  └ Цель        веха с датой                    GitHub milestone (due_on)
      └ Контур   docs/analysis/<контур>/         метка contour:*
          └ Задача  объём одного PR              issue, закрывается своим PR
```

**Бэклог не выдуман — он поднят из существующих реестров.** Каждый контур уже вёл нумерованный
реестр; issue сохраняет исходный идентификатор в заголовке, поэтому трекер и документ не
расходятся: **реестр остаётся источником содержания, issue — источником срока и состояния.**

| Реестр | Контур | Куда поднят |
|---|---|---|
| В1–В41 вопросы | `risk_appetite` | #41–#44 (блокирующие; В4 закрыт на ветке) |
| Г / Р / Д / МС / РК находки | `risk_appetite` | #45–#48 |
| Фаза 0–6, `ACTION_PLAN.md` | `npl_limits` | #37 |
| D1–D5 DoD | `risk_dwh_reconciliation` | веха О4, #50 |
| В-DPD-1…9 | `dpd15_cure` | #39 |
| В-ВОС-1…6 | `bank_recovery` | #38 |
| 10 вопросов к 4 адресатам | `nst_credit` | #40 |
| `registry/*.csv` | `risk_showcase` | #51, #52 |

### Размер задачи

Б3 уже задаёт бюджет: **7 дней и ~20 коммитов на ветку.** Медианный PR по факту — около 250
добавленных строк на 3–5 файлов. Значит, **задача = один PR, один контур, в пределах Б3.**
Что так не формулируется — это цель, а не задача, и подлежит разделению.

### Скорость — факт, не намерение

29 смёрдженных PR за 7 недель: среднее **4,1/нед.**, медиана **1/нед.**, четыре недели из
семи — ноль. 90 % слияний пришлись на две недели из семи. Планирование идёт **по медиане**:
обязательство на 4 PR в неделю — это обязательство по числу, которое случалось дважды.

Время «PR открыт» здесь ничего не измеряет (медиана 15 минут — PR самомёрджится после того,
как работа уже сделана на ветке). Реальные сигналы — **возраст ветки и возраст открытого PR**.

## 7. Что этот слой не делает

Ветки не защищены (`403 Upgrade to GitHub Pro` на приватном репозитории), Projects v2
недоступен без `read:project`. Поэтому **процесс остаётся конвенцией, а еженедельный прогон
только сообщает о нарушениях — принудить он не может.** Делать вид, что правило
обеспечено машиной, когда это не так, хуже, чем не иметь правила.

Конфиденциальность (§ 2) действует и здесь: issue и еженедельный отчёт — такое же содержимое
репозитория, как файлы. В них идут идентификаторы, счётчики, возраст и ссылки — не аналитика.

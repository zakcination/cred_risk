# Конфигурация продуктового слоя

Читается скиллом `product-manager` (`~/.claude/skills/product-manager/`). Задаёт, что в этом
репозитории считать продуктом, контуром, задачей и сроком. **Приоритет у этого файла**, а не
у общих правил скилла.

## Продукт

**Профиль рисков банка.** Поверхность — `docs/analysis/risk_showcase/` (витрина риск-метрик).
Остальные контуры — доказательная база. Спина: ДС3 и КПП. Подробнее — `ROADMAP.md`.

Аудитория: автор. Репозиторий — база знаний, где сохраняются ход работы и локальная история,
пригодные к передаче.

## Уровни

| Уровень | Поверхность |
|---|---|
| Продукт | `docs/pm/ROADMAP.md` |
| Цель | GitHub milestone с `due_on` |
| Контур | метка `contour:<имя>` |
| Задача | issue, закрывается своим PR |

Пятого уровня нет. Термины репозитория не переименовываются: контур, записка, витрина,
находка, полочка.

## Контуры

`risk_appetite` · `npl_limits` · `risk_dwh_reconciliation` · `nst_credit` · `dpd15_cure` ·
`risk_showcase` · `bank_recovery` · Stage-3 (пока без папки — issue #53).

Метка `contour:risk_dwh` соответствует каталогу `risk_dwh_reconciliation`; метка
`contour:stage3` — работе, лежащей прямо в `docs/analysis/`.

## Размер задачи

**Б3 и есть правило размера:** один PR, один контур, ≤ 7 дней, ≤ ~20 коммитов. Не подставлять
story points и прочие внешние схемы. Что не формулируется как один PR в этом бюджете — цель,
а не задача.

Планирование — **по медиане** (1–2 задачи в неделю), не по среднему (4,1). Доставка
всплесковая: четыре недели из семи — ноль.

## Что измерять

Возраст ветки и возраст открытого PR. **Не** время «PR открыт» — здесь его медиана 15 минут,
потому что PR самомёрджится после того, как работа уже сделана на ветке.

## Реестры — источник бэклога

Задачи **поднимаются** из существующих реестров, а не выдумываются. Идентификатор реестра
сохраняется в заголовке issue (`[В-ВОС-2] …`). Реестр остаётся источником содержания, issue —
источником срока и состояния.

Реестры: `В` вопросы · `Г` гипотезы · `Р` расхождения документов · `Д` дефекты отчётов ·
`МС` дефекты методики · `РК` находки по файлу рекалибровки · `Н` (dpd15) · `О` (nst) ·
`В-DPD` · `В-ВОС` · `D1–D5` (DoD сверки) · `DWH-01..16` (реестр коллеги) ·
`registry/*.csv` (витрина).

Issue не заводится на пункт, уже закрытый в источнике — в том числе закрытый **на ветке**,
которая ещё не смёрджена. Пример: В4 закрыт на `claude/ra-zapiska-v04`.

## Правила репозитория, которые слой обязан соблюдать

- **Б1** — один PR, один контур (либо один каталог верхнего уровня).
- **Б2** — ветка после слияния мертва; следующая задача начинается от `origin/main`.
- **Б3** — 7 дней / ~20 коммитов. Нарушения **сообщаются**, а не блокируются: защита веток
  недоступна (`403 Upgrade to GitHub Pro` на приватном репозитории).
- **Б5** — автор не может апрувить свой PR: draft → самопроверка → снять draft → merge.
  **Исключение важнее правила:** PR с живым ревьюером или незакрытыми пунктами на его имя не
  мёрджится без него. Это PR #19 (Сайлау) — сколько бы он ни висел.
- **Б6** — merge commit, не squash и не rebase: история PR сама по себе документ.
- **§ 2 Конфиденциальность** — действует на issue и отчёты так же, как на файлы. В трекер
  идут идентификаторы, счётчики, возраст и ссылки; аналитика, ВНД, ПДн и выгрузки — нет.
- **§ 5** — три состояния вывода: доказано на данных / взято из документа / гипотеза.
  Отзыв находки оформляется отдельным коммитом.

## Чего слой не делает

Не мёрджит, не закрывает и не удаляет ничего как побочный эффект планирования. Приземление
работы — отдельное явное решение.

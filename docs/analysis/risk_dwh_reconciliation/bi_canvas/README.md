# BI-холст процессов — Risk DWH reconciliation

Интерактивный визуальный трекер для проекта в `docs/analysis/risk_dwh_reconciliation/`:
ER-таблицы старой (`CL_PORTFOLIO.dbo` + IFRS9) и новой (`Dictionaries.risk_analytics`)
веток DWH, между ними — процессы верификации (маппинги/формулы/находки) со статусом,
историей ошибок/вопросов и версией. Дашборд по каждой новой (Dictionary) таблице
показывает долю проверенных/в процессе/непроверенных колонок.

## Файлы
- `dwh_schema_explorer.html` — сам холст. Самодостаточный HTML/CSS/JS, без внешних
  зависимостей и без сети — открывается двойным кликом в любом браузере (Chrome/Edge/Firefox).
  Данные (`TABLES`, `PROCESSES`, `QUESTIONS`, `MATRIX`) захардкожены прямо в `<script>` —
  редактируется как обычный текстовый/код-файл.
- `schema_introspection.sql` — read-only `INFORMATION_SCHEMA` скрипт (MAXDOP 1, без PII),
  которым были сверены реальные колонки всех 29 таблиц перед тем, как заполнять холст.
- `AGENT_HANDOFF_PROMPT.md` — промпт для coding-агента коллеги (Sailau, зона
  provisions/DPD/90+): критическая оценка холста → актуализация под текущее
  состояние → самостоятельные DQ-проверки, добавляемые в холст с evidence и SQL.

## Как редактировать
1. Открыть `dwh_schema_explorer.html` в редакторе кода.
2. Найти нужный блок в `<script>`:
   - `TABLES[]` — колонки таблиц (старые `old_*`, новые `new_*`).
   - `PROCESSES[]` — процессы верификации: `status`, `formula`, `inputs`, `evidence`,
     `findings`, опционально `sql`/`history`/`version`/`slice`/`pairWith`.
   - `QUESTIONS[]` — реестр открытых вопросов к S2T (сверяется с `FINDINGS.md` §7).
3. Сохранить файл и открыть/обновить в браузере — рендер полностью на клиенте.
4. Коммитить изменения на этой ветке, как обычный текстовый diff.

## Шкала статусов (5 уровней, порядок важен)

| Статус | В таблице | Что значит |
|---|---|---|
| `verified` | **зелёная заливка строки + сплошная точка** | Сверено на реальных данных, расхождений **нет вообще** — ноль исключений. Можно брать в работу как есть. |
| `proven` | зелёное **кольцо** (без заливки) | Формула/ключ доказаны, но точного совпадения по всем строкам нет. |
| `hypothesis` | жёлтая точка | Гипотеза, данными пока не закрыта. |
| `external` | жёлтая пунктирная точка | Из внешнего источника (коллеги/RAG/переписка), нами независимо не перепроверено. |
| `refuted` | серая точка | Опровергнуто данными. |

**Различать `verified` и `proven` обязательно.** Формула провизий S03 верна как формула,
а сходится на 21,23% строк — это `proven`, не `verified`. Провизии S01 сошлись
4 380/4 380 без единого исключения — это `verified`. Смешение этих двух состояний
и есть главный способ отчитаться о готовности, которой нет.

Совпадение нулей (например счёт 1845 по S17 = 0 в обеих ветках) формально `verified`,
но доказательная сила ниже: нулевое поле сходится и при неверном мэппинге. Такие
случаи помечены в `note` процесса явно.

## Шаг 0 — критическая оценка холста (30.07.2026, зона provisions/DPD/90+/стадийность)

Вывод: **недостаточно — три конкретных пробела**, все три ниже частично закрыты в этом
же коммите (см. историю `PROCESSES[]`), но не исчерпаны.

### 1. Покрытие — риск-метрики представлены слабо

Из 28 built-in `PROCESSES[]` (до этого коммита) **только 2 напрямую про
provisions/DPD** (`f4` provisions_total-формула, `f5` dpd off-by-one) + `f12`
(GL-identity `1877=18770+18771`, provisions-смежная). Ключи/grain/маппинги занимают
остальные ~25. При этом в `FINDINGS.md` уже ЗАКРЫТЫ причиной и **отсутствуют на
холсте целиком**:
- §4/§6 S03 provisions +30.6 млрд — валентный сплит (1428≈28.2 млрд → модель,
  18771≈2.3 млрд → ETL/population) — сквозной вывод, не просто identity-формула.
- §6 S17 DPD июнь→июль — 4-way cross-pairing, полностью доказанная смена расчёта
  (не лаг) — самая методологически сильная находка в файле, не отражена ни одним
  процессом.
- §6 S17 90+ теряется на 932 дог. (273.0 млн) — decomposition 247 nulled + 685
  downgraded — отсутствует.
- §7 п.14 S17 interest DPD 100% NULL (5 965 дог., 2.36 млрд 90+) — **числится в
  FINDINGS.md, но отсутствует и как процесс, и в реестре `FINDINGS{}` холста
  (там есть #1–#6, #8–#13, но нет #14 и #15)**.
- Определение Stage 3 (`category='3'`, PR #18 §6, Miras 27.07) — по духу Step 0
  прямо спрошено про "стадийность IFRS 9" — до этого коммита не было вообще.
- Открытый вопрос §7 п.5 (bucket независим от DPD — нормативное поле для 90+ не
  выбрано) — тоже не представлен как процесс.

Закрыто в этом коммите (см. `g1`–`g6` в `PROCESSES[]`): 6 новых процессов, из них
5 `proven`/`external` (импорт уже установленных в FINDINGS.md/PR#18 фактов — не
новое исследование, синхронизация) + `#14`/`#15` добавлены в `FINDINGS{}`.
S01-эквивалент DPD-скачка (FINDINGS §9.5 п.7 — "тем же методом, что закрыл S17")
всё ещё не прогнан — см. Шаг 3 ниже, это `hypothesis`, не `proven`.

### 2. Самодостаточность — частичная

Каждый `proven`/`external` процесс цитирует источник (`evidence`), но:
- Большинство built-in процессов (`f1`–`f12`) **не несут поле `sql`** — можно
  проследить ДО FINDINGS.md, но не перезапустить без него. Только `f13`, `e6`,
  `e7` (и новые `g2`/`g3`/`g4` в этом коммите) прикладывают исполняемый запрос.
- **`MATRIX[]` (панель "Сверка по источникам") вообще без `evidence`/SQL** —
  чистый хардкод-массив, статусы `✓/✗/⛔` не кликабельны и не трассируемы с холста
  напрямую. Кто не читал FINDINGS.md, не поймёт, откуда "+30.6 млрд" в ячейке S03.
- `colStatusIndex` (точки статуса у колонок) вычисляется из `PROCESSES[].inputs` —
  корректно, но у built-in процессов без `sql`-поля точка есть, а сам запрос —
  только по ссылке.

Не закрыто в этом коммите (вне зоны provisions/DPD, требует отдельной работы):
дописать `sql` на `f1`–`f11`, `d1`–`d6`; either привязать `MATRIX[]` к
`PROCESSES[]`/`FINDINGS{}` программно, либо явно пометить его как ручную сводку
с датой актуальности.

### 3. Управляемость процесса — не хватает go-live слоя

Холст визуализирует состояние, но не управляет approve:
- **Нет поля владельца/дедлайна** ни у `PROCESSES[]`, ни у `QUESTIONS[]`.
- **Нет явного статуса "готово к go-live" на уровне таблицы.** Дашборд считает
  %% колонок verified/inprog/issue/unchecked — это прокси, не решение. 6% общего
  покрытия колонок Dictionary (20/326 на момент PR #19) — тревожная цифра, но
  никак не операционализирована в "что именно блокирует переключение".
  `MATRIX[]` ближе всего к go-live-гейту (⛔ у S02), но это тоже не поле с
  явным флагом, а ручная сводка.
- `FINDINGS{}` даёт severity (`critical`/`open`/`pending`/`doc`), это частично
  замещает приоритизацию — но не привязано к "блокирует ли это конкретную
  таблицу/источник для go-live".

Не закрыто в этом коммите — вне зоны provisions/DPD (Miras/оргвопрос):
`owner`/`due`-поля в схеме `PROCESSES[]`/`QUESTIONS[]`, per-table go-live флаг,
явная связка "открытый вопрос → блокирует какую таблицу".

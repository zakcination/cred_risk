## 1. Цель и основания разработки

В рамках ключевого показателя эффективности «Развитие DWH и контроль качества данных» на III квартал 2026 года разработан порядок тестирования новой витрины рисков Dictionaries.risk_analytics (далее – витрина).

Целью настоящего документа является закрепление методологии тестирования витрины и порядка подготовки тестирования. Методология должна обеспечить перевод отчётности Блока риск-менеджмента (далее – БРМ) на витрину без повторного разбора её данных.

Документ сформирован на основе практики тестирования витрины, проводимого с июля 2026 года. Каждое правило подтверждено случаем, когда его несоблюдение привело к повторному прогону либо к ошибочному выводу.

Результаты первого цикла тестирования и взаимодействие с подразделением информационных технологий (далее – БИТ) изложены в отдельном отчёте по тестированию.

## 2. Объект тестирования

Витрина объединяет данные по займам четырёх систем-источников. Базой сравнения служит прежняя ветка хранилища CL_PORTFOLIO (далее – прежняя ветка). До завершения сверки она остаётся вторым независимым измерением тех же займов.

Таблица 1. Системы-источники витрины
| Код | Система | Таблицы прежней ветки |
|---|---|---|
| S01 | RS, розничное ядро | PORTFOLIO_RS |
| S02 | карточные продукты: Way4, SMARTCARD, Installment, kpk, Payda | три таблицы PORTFOLIO_CREDITCARDS |
| S03 | CrediLogic, основная выдача | CL_PORTFOLIO_2 |
| S17 | Fenix | PORTFOLIO_Fenix |

Спецификация витрины отсутствует, разработчик витрины для консультаций недоступен. В связи с этим любое утверждение о данных витрины подтверждается на самих данных. Документация, наименования полей и схемы рассматриваются как предположения, подлежащие проверке.

Результатом тестирования является доказанная основа для перевода отчётности: по каждой таблице — подтверждённые ключи связи, гранулярность, даты и формулы; по каждому полю — заключение о пригодности к использованию.

## 3. Принципы тестирования

Тестирование основано на семи принципах. Для каждого указан случай, подтвердивший его необходимость.

Таблица 2. Принципы тестирования
| № | Принцип | Случай из практики |
|---|---|---|
| 1 | Утверждение о данных подтверждается только на данных; наименование поля не определяет его содержание | поле l_rate содержит наименование кредитной программы, а не процентную ставку: ни одно из 8 259 299 значений не является числом |
| 2 | Каждый вывод имеет один из трёх статусов: подтверждён, открыт, опровергнут. Опровергнутые выводы сохраняются с причиной отзыва | повторная ошибка на уже снятом выводе вероятнее новой |
| 3 | Проверка идёт от основания к показателям; следующий уровень проверяется после объяснения причины результата на предыдущем | сумма, рассчитанная при размножении строк в соединении таблиц, достоверной величиной не является |
| 4 | Без эталона вывод о том, какая из веток верна, не делается | по расхождению провизий S03 на 30,6 млрд ₸ без бухгалтерского эталона нельзя определить, переоценивает ли резервы витрина или недорезервирует прежняя ветка |
| 5 | Каждая величина воспроизводится вторым, независимо составленным запросом | два сценария независимо дали одинаковую численность — 8 259 299 строк |
| 6 | Ошибка скрипта отделяется от дефекта витрины до направления сведений в БИТ | первый прогон послойной проверки выявил шесть ошибок скрипта, а не витрины |
| 7 | Выполняются только запросы на чтение, выводятся только агрегированные данные | вывод персональных данных одним из сценариев исправлен по результатам прогона |

## 4. Структура тестирования

Тестирование включает шесть видов проверок. Каждый вид отвечает на самостоятельный вопрос и не заменяет остальные.

Таблица 3. Виды проверок
| Вид проверки | Вопрос | Объём |
|---|---|---|
| Послойная проверка | можно ли использовать таблицу как основание для следующей | 71 проверка в 14 слоях |
| Сценарии аналитика | может ли витрина ответить на типовые запросы аналитиков | 100 сценариев трёх уровней сложности |
| Пробы | какое из двух объяснений результата верно | по одной пробе на вопрос; 13 проб |
| Кейс-прогоны | воспроизводимое подтверждение конкретного дефекта для БИТ | 5 скриптов |
| Сверка с прежней веткой | какие договоры утрачены и совпадают ли суммы | состав портфеля, остатки, провизии, просрочка по каждому источнику |
| Проверка полноты по плану счетов | все ли счета займов входят в формулы остатков | 8 проверок |

### 4.1. Послойная проверка

Слои проверяются в порядке зависимости. Если нижний слой не пройден, результаты верхних слоёв рассчитываются, но помечаются как недостоверные.

Таблица 4. Слои послойной проверки
| Слой | Предмет проверки |
|---|---|
| L0 | схема и домены: типы ключей, справочник источников, выравнивание дат |
| L1 | основная таблица договоров: гранулярность и уникальность ключа |
| L2 | перечень действующих договоров |
| L3 | остатки на отчётную дату по 25 счетам главной книги |
| L4 | заёмщики и ссылочная целостность |
| L5 | состав портфеля в прежней ветке и в витрине |
| L6 | остатки по совпавшим договорам |
| L7 | провизии |
| L8 | просрочка и договоры с просрочкой свыше 90 дней |
| L9 | залоги |
| L10 | выбытие: списания, взыскание, внебалансовый учёт |
| L11 | графики и платежи |
| L12 | прочие таблицы: рейтинги, ставки, гарантии, кредитные линии, реструктуризации |
| L13 | итоговая витрина показателей |

### 4.2. Сценарии аналитика

Сценарии разделены на три уровня сложности: простые — по одной таблице, средние — по связям между таблицами, сложные — по динамике и итоговым показателям.

Для каждого сценария указано не только содержание расчёта, но и ошибка, на которой он может дать неверный результат. Сценарий, выполнение которого невозможно из-за известного дефекта, показывает границу пригодности витрины и поэтому не менее ценен, чем успешно выполненный.

## 5. Порядок проверки

Проверка выполняется в установленной последовательности. Переход к следующему шагу допускается после объяснения причины результата предыдущего шага, а не только после получения числа.

Таблица 5. Последовательность проверки
| Шаг | Содержание | Обоснование |
|---|---|---|
| 1 | схема и типы ключевых полей по системному каталогу | до соединения таблиц: типы ключей различаются (текст против целого числа) |
| 2 | единство справочника источников | один ли справочник S01, S02, S03, S17 во всех таблицах |
| 3 | гранулярность: число строк против числа уникальных ключей | размножение строк выявляется до суммирования |
| 4 | выбор ключа по покрытию среди всех кандидатов | номер договора не уникален: 9 659 совпадений между источниками |
| 5 | приведение дат к первому числу месяца | обе ветки ведут даты на первое число |
| 6 | состав портфеля: совпавшие договоры, только в прежней ветке, только в витрине | отсутствие договора и расхождение суммы — разные дефекты |
| 7 | остатки по совпавшим договорам | сначала счета, затем расчётные величины |
| 8 | экономическое содержание: остаток и его движение | до вывода о том, какая ветка ошибается |
| 9 | провизии, просрочка, договоры 90+ | риск-параметры влияют на регуляторные показатели |
| 10 | выбытие | отсутствие записи допустимо для части источников |

## 6. Критерии прохождения

Сценарий считается пройденным при одновременном выполнении четырёх условий:
- использован подтверждённый ключ связи, а не поле со схожим наименованием;
- пустое значение отделено от нуля и от отсутствия записи;
- результат воспроизведён вторым, независимо составленным запросом;
- различия между источниками отражены в разрезе источников, а не усреднены.

Вывод по результатам тестирования имеет один из трёх статусов: подтверждён, открыт, опровергнут. Заключение по полю витрины — одно из трёх: пригодно, пригодно с оговоркой, непригодно.

Контрольные показатели сценария, включая долю неизвестных значений, учитываются в заключении по сценарию, а не приводятся отдельно от него.

При этом необходимо отметить, что указанное правило введено по итогам конкретного случая: доля незаполненных значений просрочки была выведена в результатах прогона сценариев, однако учтена только после отдельной пробы.

## 7. Типовые ошибки проверки

Библиотека сценариев содержит 48 описанных ошибок — случаев, когда корректно поставленный вопрос даёт неверный ответ на данных витрины. Они сводятся к семи типам.

Таблица 6. Типы ошибок проверки
| Тип ошибки | Пример |
|---|---|
| наименование поля не соответствует содержанию | поле l_rate содержит наименование программы; поле la_loan_id не связывает договоры S03 |
| пустое значение принимается за нуль | при толковании пустой просрочки как нуля доля 90+ составляет 14%, при толковании как неизвестной — 67% |
| внутреннее соединение не видит договоров, отсутствующих в одной из веток | провизии и просрочка по спорным договорам выпадают из расчёта |
| нулевой результат по нескольким таблицам вызван неверным ключом | до вывода об отсутствии данных проверяется другой ключ |
| промежуточная группировка лишает проверку содержания | группировка по ключу до подсчёта дублей по тому же ключу |
| отчётная дата отсутствует в витрине | запрос на 01.07.2026 вернул нулевой результат: срез перезаписан |
| наличие записи не означает действующий договор | необходимы статус и движение остатка |

## 8. Требования к скриптам

Скрипты тестирования соответствуют следующим требованиям:
- выполняются только запросы на чтение; временные таблицы создаются с префиксом, уникальным для скрипта;
- ресурсоёмкие запросы выполняются с ограничением параллелизма;
- объекты указываются полным именем с наименованием базы данных, поскольку при сокращённом имени запрос к системному каталогу другой базы возвращает пустой результат без ошибки;
- наименования полей берутся из системного каталога, а не из схемы визуализации, которая расходилась с базой данных не менее чем по трём полям;
- нормализация ключа выполняется однократно для проверки, а не в каждом соединении, поскольку иначе соединение перестаёт использовать индекс;
- фильтр применяется до размножения строк, а не после;
- даты, допуски и источники задаются параметрами;
- сначала рассчитываются агрегаты, затем детализация.

## 9. Подготовка цикла тестирования

Перед каждым прогоном выполняются семь шагов подготовки.

Таблица 7. Подготовка прогона
| № | Шаг | Какую ошибку предотвращает |
|---|---|---|
| 1 | проверка схемы той таблицы, к которой обращается запрос, отдельным пакетом | обращение к несуществующему полю |
| 2 | отчётная дата определяется как последняя дата каждого источника, а не общая | S03 загружен на месяц вперёд, и общая дата показала бы только его |
| 3 | контроль численности двумя независимыми итогами | нулевой результат из-за утраченного фильтра |
| 4 | статическая проверка текста скрипта до запуска | перед прогоном №2 выявлено 10 ошибок текста, из них 3 давали ложное прохождение проверки |
| 5 | разбиение скрипта на независимые пакеты | сбой одного пакета не прерывает остальные |
| 6 | самопроверка скрипта и результата до передачи: ключ, знаменатель, персональные данные | самопроверка сценариев третьего уровня выявила три ошибки до передачи |
| 7 | сохранение агрегатов прогона на стороне БРМ | витрина хранит историю одной таблицы из четырнадцати, и после перезагрузки результат не воспроизводится |

## 10. Передача сведений о дефектах в БИТ

Перед направлением сведений о дефекте в БИТ выполняются пять проверок:
- ключ связи подтверждён покрытием, а не наименованием поля;
- дефект не объясняется датой среза или фильтром;
- величина дефекта измерена в сумме и в числе договоров по каждому источнику;
- приложен скрипт, воспроизводимый на стороне БИТ;
- исключена ошибка самого скрипта: вывод подтверждён независимой проверкой.

Письмо о дефекте содержит описание выявленного, порядок воспроизведения, величину дефекта, требуемое от получателя действие и перечень того, что письмом не утверждается.

Поскольку витрина перезаписывается без сохранения истории, письмо привязывается к дате среза.

## 11. Распределение ответственности

Таблица 8. Участники тестирования
| Участник | Зона ответственности |
|---|---|
| БРМ, направление риск-метрик | ключи связи, гранулярность, состав портфеля, спорные договоры; реестры полей и связей |
| Независимая ветка проверки | провизии, просрочка, договоры 90+; независимый реестр дефектов; рецензирование послойной проверки |
| БИТ, разработчик витрины | получение сведений о дефектах, исправление, разъяснение правил загрузки |
| Руководство департамента | рассмотрение эскалаций; решения, выходящие за пределы данных |

Две ветки проверки ведутся независимо и сверяются между собой. Результаты одной ветки включаются в совместное письмо только после их перепроверки методом другой.

## 12. Периодичность тестирования

Предлагается следующая периодичность:
- регрессионный прогон послойной проверки — после каждого изменения витрины, о котором сообщает БИТ, и перед переводом каждого отчёта на витрину;
- повторная проверка направленного дефекта — после ответа БИТ, с письменным подтверждением исправления;
- обновление реестров полей и связей — по каждому прогону, в котором получен новый факт.

**Указанная периодичность является предложением и подлежит утверждению.**

## 13. Ограничения

При применении методологии следует учитывать её ограничения:
- методология сравнивает витрину с прежней веткой и с ней самой; бухгалтерского эталона она не содержит, поэтому при расхождении веток фиксирует расхождение, но не определяет, какая из них верна;
- витрина хранит историю только одной таблицы из четырнадцати, и проверка динамики возможна только по ней;
- производительность витрины и регламент загрузки предметом тестирования не являются.

## 14. Выводы

По результатам разработки установлено следующее.

1. Методология тестирования витрины закреплена: семь принципов, шесть видов проверок, последовательность проверки из десяти шагов и критерии прохождения.
2. Каждое правило методологии подтверждено практикой тестирования, проводимого с июля 2026 года.
3. Порядок подготовки прогона из семи шагов предотвращает ошибки, выявленные в предыдущих прогонах, включая десять ошибок текста скрипта, найденных до прогона №2.
4. Порядок передачи дефектов в БИТ исключает направление ошибок скрипта в качестве дефектов витрины.
5. Методология не заменяет бухгалтерский эталон: при расхождении провизий вопрос о том, какая ветка верна, требует отдельного решения.

## 15. Предложения

С учётом изложенного предлагается:

1. Принять настоящий порядок в качестве методологии тестирования витрины рисков.
2. Рассмотреть вопрос об утверждении периодичности регрессионных прогонов, указанной в разделе 12.
3. Провести прогон №2 послойной проверки после исправления ошибок, выявленных статической проверкой, совместно с независимой веткой проверки.
4. Определить источник бухгалтерского эталона для оценки расхождений по провизиям.

- Реестр скриптов тестирования.
- Руководство по передаче сведений о дефектах.

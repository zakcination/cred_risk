## 2. GRAIN / ДАТЫ — CONFIRMED
- `loans` grain по gid — **UNRESOLVED, повторно открыт 17.07** (2-й самостоятельный ревьюер
  поймал методологическую ошибку в моей проверке от того же дня). Запрос `GROUP BY source,gid`
  во ВНУТРЕННЕМ подзапросе схлопывает все сырые строки одного `(source,gid)` — включая
  потенциальные дубли **внутри одной даты** — ДО того, как внешний `COUNT(*)` вообще запускается.
  Внешнее равенство `rows_all=distinct_gid` было тавтологией структуры запроса (подзапрос уже
  даёт ровно 1 строку на `(source,gid)` по конструкции), не эмпирическим фактом. **"CONFIRMED
  SAFE" отозвано.** Реально проверено (тем же 17.07-запросом) только: один `gid` не встречается
  на разных `l_report_date` одновременно (это `MAX(dup_dates)=1` в подзапросе — этот конкретный
  срез сигнала не был затронут багом). Дубли **внутри одной даты** — не проверены вовсе.
  Корректный тест — см. §9.6.
  **Побочная гипотеза "gid чеканится заново на каждую загрузку" — тоже отозвана как
  недоказанная.** Сделана только из разницы объёмов (7.1М distinct gid у S03 vs 237K активных на
  одну дату), а это можно объяснить и накоплением закрытых/исторических договоров без чеканки
  нового gid. Правильный тест — один business-key (`l_loan_number`) на нескольких датах,
  подсчёт `COUNT(DISTINCT l_gid)` — см. §9.6.
  **Что НЕ отзывается:** практические grain-gate этой сессии (A5/A10/A14 в архиве) устроены
  иначе — прямой `JOIN loan_account→loans` с фильтром по одной дате на стороне `loan_account`,
  `COUNT(*)` **после** join, без предварительного `GROUP BY`. Этот паттерн бага не имеет: если бы
  `loans` дал 2 строки на тот же gid, join размножил бы результат, и это было бы видно в
  `COUNT(*)>COUNT(DISTINCT...)`. Эмпирически не произошло (S03 2026-07-01: 237 386=237 386 и
  т.д.) — узкий вывод "fan-out не проявился для gid, реально задействованных в S02/S03/S17
  реестре §6" остаётся в силе. Общий вывод "loans всегда 1 строка/gid для любого gid" — нет.
- `loan_account` grain чист по S01/S02/S03. **S17 — 1 коллизия `dog_num`/снимок** (gid безопаснее).
- Population определяется членством в **loan_account** на `la_reporting_date`
  (у `loans` снимка нет).
- Даты обеих ветвей — **month-start** (…-01). S03: маппинг дат не нужен.
- OLD `CL_PORTFOLIO_2` — дневная история 2012→2026, но эффективно month-start срезы.

### 9.4.1 Раунд 2 — самоаудит нашей же проверки (второй независимый ревьюер, 17.07)

### 9.6 Запросы для пп. 1 (исправлено) и 2 (не прогнаны)

**Прежний запрос п.1 (см. историю коммитов) был методологически некорректен** — паразитный
`GROUP BY source,l_gid` в подзапросе схлопывал именно ту размерность, дубли по которой
проверялись, до того как внешний `COUNT(*)` запускался; равенство `rows_all=distinct_gid` было
тавтологией конструкции запроса. Ниже — исправленная версия (без предварительного схлопывания
сырых строк) и отдельный тест на стабильность gid по business-ключу.

```sql
/* ИСПРАВЛЕНО 17.07 (round 2). Grain loans ВНУТРИ ОДНОЙ ДАТЫ — прямой тест, без паразитного
   GROUP BY перед подсчётом сырых строк: raw_rows = SUM(grp_size), считанный ПОСЛЕ группировки,
   а не COUNT(*) НАД уже сгруппированным набором (разница ровно в том, что сломало прошлый тест).
   читать: (a) duplicate_extra_rows=0 везде И max_rows_per_gid_per_date=1 → grain действительно
              чист внутри даты, gid=1428/9.4 п.1 закрывается по-настоящему;
           (b) duplicate_extra_rows>0 → есть сырые дубли (source,gid,date) — join la_gid=l_gid
              БЕЗ фильтра report_date на стороне loans может размножить строки для этих
              конкретных gid; нужно поднять затронутые source/дату отдельно. */
SELECT l_source,
       SUM(grp_size) AS raw_rows,
       COUNT(*) AS distinct_gid_date_groups,
       SUM(grp_size) - COUNT(*) AS duplicate_extra_rows,
       MAX(grp_size) AS max_rows_per_gid_per_date
FROM (
  SELECT l_source, l_gid, l_report_date, COUNT(*) AS grp_size
  FROM Dictionaries.risk_analytics.loans
  GROUP BY l_source, l_gid, l_report_date
) x
GROUP BY l_source
OPTION (MAXDOP 1);

/* Business-key (l_loan_number) → сколько РАЗНЫХ gid получает через разные report_date?
   Закрывает вторую отозванную гипотезу ("gid чеканится заново на каждую загрузку").
   читать: (a) keys_with_multiple_gid≈0 при keys_seen_multiple_dates>0 → gid стабилен по
              business-ключу, гипотеза "чеканится заново" НЕ подтверждается, разница объёмов —
              просто накопленная история без переиздания gid;
           (b) keys_with_multiple_gid растёт вместе с keys_seen_multiple_dates (близко к 1:1) →
              гипотеза подтверждается — тот же договор получает новый gid на каждой загрузке. */
SELECT l_source,
       COUNT(*) AS distinct_business_keys,
       SUM(CASE WHEN distinct_gid = 1 THEN 1 ELSE 0 END) AS keys_with_one_gid,
       SUM(CASE WHEN distinct_gid > 1 THEN 1 ELSE 0 END) AS keys_with_multiple_gid,
       MAX(distinct_gid) AS max_gid_per_key,
       SUM(CASE WHEN dup_dates > 1 THEN 1 ELSE 0 END) AS keys_seen_multiple_dates
FROM (
  SELECT l_source, l_loan_number,
         COUNT(DISTINCT l_gid) AS distinct_gid,
         COUNT(DISTINCT l_report_date) AS dup_dates
  FROM Dictionaries.risk_analytics.loans
  WHERE l_loan_number IS NOT NULL
  GROUP BY l_source, l_loan_number
) y
GROUP BY l_source
OPTION (MAXDOP 1);

/* S03 pledges через Source+l_gid вместо la_loan_id — закрывает пункт 3 (§9.4).
   читать: если баланс/периметр 49-договорной находки (DWH-15) меняется относительно
   la_loan_id-версии — цифра 367.7М была артефактом неверного ключа, не фактом. */

--  la.la_loan_id = t.loan_id
--  на la.la_gid = t.l_gid AND la.la_source = N'S03')
```

- **A1a — `c_bpm_object_id` НЕ универсален.** 100% заполнен для S01/S17, **0% для

**Контраргумент (проверен, не снимает вывод, но фиксируется явно):** гипотетически

### 12.1 Вывод

**В таблице `loans` числовой ставки нет ни одной колонки.** Оба «ставочных» поля
там — varchar, и одно из них занято названием кредитной программы. Ставка живёт
в **отдельной таблице `risk_analytics.interest_rates`**, grain которой канвас
описывает как `contract · dlcr_dog_num`:

```
report_date  dlcr_dog_num(nvarchar 35)  [dlcr$source]  loan_id(bigint)
interest_rate  initial_nominal_rate  effective_rate  initial_effective_rate
```

**`effective_rate` — это и есть ГЭСВ/APR, то самое «AIER» из исходного запроса
аналитиков.** То есть вопрос «выгрузить условия кредита с AIER» выполним — но
не по `loans`, а через `interest_rates`, и только после проверки связки.

### 12.2 Почему это не «просто взять ставку»

`interest_rates` до сих пор числилась в разделе «что набор НЕ покрывает»
(`DWH_TEST_SCENARIOS.md`): у неё нет ни дубль-чека, ни проверки покрытия.
Присоединять её к портфелю нельзя, пока не доказаны четыре вещи — их проверяет
проба **P8** (`DWH_PROBE_P8_INTEREST_RATES.sql`):

- **Сетка дат по источникам.** Прямой урок P1: общий `@AsOf` оставил один S03,
  и это выглядело как «данных нет».
- **Grain.** Если на договор больше одной строки, JOIN размножит суммы портфеля.
- **Рабочий ключ по покрытию.** **Gid-колонки у таблицы НЕТ** — канонический путь
  `*_gid = l_gid` недоступен. Кандидаты `loan_id` (bigint) и `dlcr_dog_num`
  (nvarchar). Имени не верим: `la_loan_id` тоже звучал как ключ и дал 0
  совпадений по S03 (T2).
- **Единица измерения.** `effective_rate` объявлен `numeric(18,9)`, три остальных
  — `(17,2)`. Разная шкала — сигнал, что одно поле хранит долю (`0.185`), а другие
  проценты (`18.50`). Смешение в одном отчёте даёт **ошибку в 100 раз**.

### 12.3 Побочный результат: M39 в L2B разблокирован

`loan_account.currency_exchange_rate` **существует** (numeric(18,2)). Сценарий
M39 был написан как «подготовка популяции» именно потому, что имя не было
подтверждено. Теперь сравнение курсов внутри среза можно достроить.

### 12.4 Что это меняет в приоритетах

`interest_rates` из «не покрыто, отдельная программа» переходит в **критический
путь**: без неё нет ни ставки, ни AIER, ни маржи, ни ценового анализа — то есть
не закрывается исходный запрос аналитиков целиком. P8 — следующий шаг.

## 13. Проба P8 — паспорт `interest_rates`. Ключ найден, но шкала сломана

### 13.1 СНАЧАЛА — дефект в самой пробе (иначе вывод ниже прочитается неверно)

P8d показал `dlcr_dog_num -> l_loan_number` = **100,0000% на всех четырёх
источниках**. Цифра выглядит идеальной, но **тест написан неверно**: джойн шёл

даёт **9 659 коллизий между источниками**, то есть строка ставки S01 могла
совпасть с номером договора S03 и засчитаться как матч.

**100% — верхняя граница, а не доказанное покрытие.** Это ровно тот запрет из

на который я сам и наступил. Переписано в **P9** на пару `(source, номер)`.

### 13.2 Что установлено твёрдо

**Историзации нет.** Одна дата — `2026-08-01`, у всех четырёх источников,
совпадает с `loans`. В отличие от `loan_account` (19–20 срезов) и

Динамика ценообразования и репрайсинг невыполнимы.

**Grain чистый.** На паре `(source, date, dlcr_dog_num)` — **одна** дублирующаяся
пара на всю таблицу (S01, 2 строки, 1 избыточная). JOIN не размножит портфель.

**Покрытие портфеля строками — по источникам разное и местами почти нулевое.**

### 13.3 `loan_id` не работает — снова T2

### 13.4 ГЛАВНОЕ: две шкалы внутри одной колонки

| source | `interest_rate` | `effective_rate` (ГЭСВ) | `initial_nominal_rate` | `initial_effective_rate` |
|---|---|---|---|---|
| S01 | 0,01–47,00 | 0,0–**178,80** | 0–47,00 | 0,01–47,00 |
| S02 | 12,00–39,90 | **100% NULL** | 12,00–39,90 | **100% NULL** |
| S03 | 0,01–99,99 | 0,0–**999,00** | 0–99,99 | 0–**999,00** |
| S17 | 0,12–43,00 | 0,0–56,00 | 0–43,00 | **100% NULL** |

**1. Значения (0;1] и (1;100] сосуществуют в ОДНОЙ колонке и ОДНОМ источнике:**

| поле / source | в (0;1] | в (1;100] |
|---|---:|---:|
| `interest_rate` S03 | **1 509 608** | 5 099 596 |
| `interest_rate` S17 | **195 480 (68%)** | 92 919 |
| `initial_nominal_rate` S03 | **1 533 275** | 5 056 441 |
| `effective_rate` S03 | 1 077 578 | 5 495 190 |

Средние это подтверждают арифметически: у S17 `ir_avg = 10,30` при 68% значений
ниже единицы — такое среднее получается только смешением ~93 тыс. процентов
(~32) со ~195 тыс. долей (~0,3). **Одна колонка хранит и проценты, и доли.**
Любой `AVG(interest_rate)` сегодня занижен, а фильтр «ставка > 20%» теряет
все строки, записанные долей.

**2. Разные поля на ОДНОЙ строке в разных шкалах — отсюда инверсии ГЭСВ.**
P8g: ГЭСВ ниже номинальной у S03 на **1 039 284** строках (15,7%). Счёт почти
совпадает с числом строк, где `effective_rate` записан долей (1 077 578), а
`interest_rate` — процентом. Экономически ГЭСВ не может быть ниже номинальной
(он включает комиссии) — значит это не экономика, а шкала.

**3. У S17 инверсия имеет ДРУГУЮ причину — ноль вместо пропуска.**
ГЭСВ ниже номинальной на **228 744 из 288 399 (79%)**, и при этом
`effective_rate = 0` на **220 077 строках (76%)**. Это не APR = 0%, а
незаполненное поле, закодированное нулём (`NULL ≠ 0`, `CLAUDE.md`).
Средний ГЭСВ по S17 (`5,97`) занижен втрое именно из-за этих нулей.

**4. Значение-заглушка 999.** У S03 `effective_rate` > 100 на **16 482** строках
при максимуме ровно `999,000000`; `initial_effective_rate` — на 16 510 строках,
максимум тоже `999,0`. У S01 максимум ГЭСВ `178,80` (283 строки > 100).
`999` — техническая заглушка, в расчёт не брать.

### 13.5 Практический итог для аналитики

| Вопрос аналитика | Ответ на сегодня |
|---|---|
| Номинальная ставка по договору | Есть, но **шкала не единая** — до нормализации не агрегировать |
| ГЭСВ / AIER | **S02 — нет вообще** (100% NULL). S17 — 76% нулей-заглушек. S01/S03 — есть, но с примесью долей и заглушек `999` |
| Ставка на прошлую дату | **Невыполнимо** — одна дата, историзации нет |
| Ставка по всему портфелю | Максимум 84,4% договоров; у S02 — 6,4% |

**Нормализация шкалы возможна** (значение < 1 → умножить на 100), но это
**гипотеза, а не факт**: строка со ставкой `0,5` может быть и «0,5%», и «50%».
Разводится сопоставлением с кредитной программой из `l_rate` (§11.1): если
внутри ОДНОЙ программы встречаются обе шкалы — это дефект загрузки, и правило
×100 применимо; если программы разделены по шкалам — значения могут быть
корректны, и правило сломает данные. Проверяет **P9**.

### 13.6 Второй, мелкий дефект пробы

Параметр `@PctLo = 0.5` оказался мёртвым: ветка `WHEN v < @PctLo` стоит после
`WHEN v <= 1`, поэтому недостижима. Фактические бакеты — `(0;1]` и `(1;100]`.
На выводы не влияет (границей всё равно служит единица), но параметр не делал
того, для чего был заведён. В P9 порог убран как лишняя сущность.

### 14.1 ОПРОВЕРГНУТ МОЙ ЖЕ ВЫВОД §13.3: у `interest_rates` ЕСТЬ gid

В §13.3 я написал: «Gid-колонки у таблицы НЕТ, канонический путь `*_gid = l_gid`
недоступен» и «третья колонка с именем `*loan_id*`, не являющаяся ключом к `loans`».
**Оба утверждения неверны.**

P9b/P9c: `loan_id` заполнен на 100% (0 NULL, 0 нулей), **всегда 18 разрядов**,
`distinct = rows_total` во всех источниках. Диапазоны:

| source | min | max | префикс |
|---|---|---|---|
| S01 | 100000000000075116 | 100000000219830116 | **10** |
| S02 | 110000000796451116 | 110001086113600116 | **11** |
| S03 | 120000000000021116 | 120000007127199116 | **12** |
| S17 | 270000000006173116 | 270000000558181116 | **27** |

Это в точности карта префиксов gid из **T17** (10=S01, 11=S02, 12=S03, 27=S17).
P9d подтверждает покрытием: **`loan_id → l_gid` = 100,0000% на всех четырёх
источниках**.

**`interest_rates.loan_id` — это gid, а не loan_id.** Колонка названа неверно.

**Почему я ошибся.** В P8d я протестировал единственную связку, которую подсказывало
имя колонки — `loan_id → l_loan_id`. Она честно дала 0%, и вердикт «не работает» для
неё был верен. Ошибка в том, что я обобщил его до «у таблицы нет gid», не проверив
вторую связку. Это ровно тот антипаттерн, который стоит первым в `CLAUDE.md`
(«имя колонки ≠ семантика»): я не поверил имени в одну сторону, но поверил в другую —
раз колонка называется `loan_id`, то gid искать негде.

**Следствие: канонический путь восстановлен.** `interest_rates` соединяется с
портфелем как все остальные таблицы — `loan_id = l_gid`, одна колонка, bigint,
`l_gid` глобально уникален, `source` не нужен. Это лучше связки по номеру: gid
уникален построчно (`distinct = rows`), тогда как у `dlcr_dog_num` есть одна
дублирующаяся пара в S01 (P8b) — то есть один номер договора несёт два разных gid.

### 14.4 Шкала: дефект ПОДТВЕРЖДЁН, но правило ×100 применять нельзя

P9f сопоставил шкалу с кредитной программой (`l_rate`):

| source | обе шкалы в одной программе | вся в (1;100] | вся в (0;1] |
|---|---|---|---|
| S01 | **6 программ / 12 672 дог.** | 111 / 22 067 | — |
| S02 | — | 1 199 / 38 619 | — |
| S03 | **191 / 1 689 678** | 5 089 / 4 916 812 | 428 / 2 714 |
| S17 | **32 / 18 225** | 167 / 91 907 | **72 / 178 267** |

**Дефект подтверждён.** 229 программ (S01/S03/S17) содержат договоры в обеих шкалах
одновременно — **1 720 575 договоров**. Внутри одного продукта у части договоров
ставка записана как `0,185`, у части как `18,5`. Свойством продукта это быть не может.

**Но механическое `< 1 → ×100` применять НЕЛЬЗЯ по двум независимым причинам:**

**1. P9g: на 18% смешанных программ ×100 не попадает в диапазон.**

| source | смешанных программ | ×100 попадает | ×100 НЕ попадает |
|---|---:|---:|---:|
| S01 | 6 | 4 | **2** |
| S03 | 191 | 160 | **31** |
| S17 | 32 | 23 | **9** |
| **Итого** | **229** | 187 (81,7%) | **42 (18,3%)** |

Правило верно примерно в четырёх случаях из пяти. Слепое применение тихо испортит
42 программы, и отличить испорченные от исправленных потом будет нечем.

**2. У S17 основная масса — программы ЦЕЛИКОМ в доле.** 72 программы / **178 267
договоров** (68% источника) не содержат ни одного «процентного» значения. Внутренней
проверкой это не разводится: программа целиком в `(0;1]` одинаково согласуется и с
«вся программа хранится долей» (тогда ×100 верно), и с «это реально ставки ниже 1%»
(тогда ×100 завысит ставку в 100 раз). Ответ — только у автора марта.

**S02 — единственный чистый источник по шкале:** 1 199 программ, все целиком в
`(1;100]`, диапазон 12,00–39,90. Но покрытие 8,86% и ГЭСВ отсутствует полностью.

### 14.5 Уточнение §13.4 п.4: заглушки `999` почти нет

Я записал «`effective_rate` > 100 у S03 на 16 482 строках при максимуме ровно 999 —
техническая заглушка». **Это смешало две разные вещи.** P9h разделил:

|---|---:|---:|---:|

Заглушек ровно **35** (плюс 35 в `initial_effective_rate`). Остальные 16 447 — обычные
значения между 100% и 999%, и для короткого POS-кредитования ГЭСВ выше 100% годовых
**правдоподобен**, а не дефектен. Как дефект в реестр идут только 35 строк.

### 14.6 Ноль вместо пропуска — подтверждён экономически

`interest_rate = 0` **не встречается нигде** (`ir_zero = 0` во всех источниках).
При этом `effective_rate = 0`:

| source | ГЭСВ = 0 | из них с положительной номинальной |
|---|---:|---:|
| S01 | 186 | **186 (100%)** |
| S03 | 6 009 | **6 009 (100%)** |

Не «мало», а ноль. Контроль арифметикой, а не доверием к выводу: шаг 2 отобрал

Источник с живым портфелем и нулём 90+ — это не чистая книга. Это либо

### 16.2 T13 (off-by-one) — цена вопроса измерена

Оба определения посчитаны рядом. Разница между `days_past_due > 90` и

| источник | Δ договоров | Δ экспозиции, ₸ | Δ непокрытой, ₸ |
|---|---|---|---|

| S17 | 5 | 559 831 | 559 831 |
| **итого** | **30** | **89 130 918** | **33 674 280** |

То есть выбор определения двигает регуляторную цифру на **33,7 млн ₸** (0,18%).
Мало по доле — но это ровно тот случай, когда важно не «много ли», а «известно
ли». Пока определение не зафиксировано в документе, две команды получат два
разных числа и обе будут правы.

По S01 оба определения дали **идентичный** результат: ни одного договора с
`days_past_due` ровно 91. На 289 договорах это возможно случайно, но заодно
согласуется с подозрением, что DPD у S01 может быть не посуточным. Отдельно не
проверялось.

### 16.3 Почему недопокрытие считается поконтрактно

Агрегатное покрытие у S01 — 576%, у S03 — 208%. По агрегату оба выглядят
«обеспеченными с запасом». Поконтрактно у них 1,3 млрд и 16,1 млрд ₸
недопокрытия. Залог сконцентрирован: у S03 **56,9%** договоров 90+ не имеют
залога вообще, у S01 — **61,6%**.

Разница агрегатов здесь не консервативнее, а просто неверна: она позволяет
избытку обеспечения по одному договору гасить необеспеченность другого, чего
при взыскании не происходит.

### 16.4 S17: просрочка 90+ практически необеспечена

7 131 договор из 7 153 (**99,7%**) без залога; покрытие 6,6%; непокрыто 94,1%
экспозиции. Средняя экспозиция 400 тыс. ₸ — похоже на беззалоговую розницу, и
тогда это не дефект данных, а профиль продукта. Но подтверждения продуктовым
справочником у нас нет, поэтому в отчёт это идёт как **наблюдение**, а не как
вывод «портфель необеспечен».

Для контекста: средняя экспозиция 90+ у S01 — 103 млн ₸ (корпоративная книга),
у S03 — 1,7 млн ₸. Три источника ведут три разные книги, и сводить их
недопокрытие в одну цифру без оговорки нельзя.

### 16.5 Границы этой цифры — перечислены полностью

1. **Даты не совпадают.** `pledges` — один срез, 2026-08-01 (истории нет,
   §10). Последний срез `loan_account`: S03 — 2026-08-01, а S01/S02/S17 —
   2026-07-01. То есть по трём источникам обеспечение берётся на дату, которой
   в портфеле нет, и выровнять это невозможно: старого среза залогов не
   существует. Для S03 даты совпадают.
2. **Залог во float** (`c_collateral_value`, §15). На 43 тыс. строк ошибка
   накопления — единицы тенге, для величины несущественно. Существенно другое:
   такие суммы **нельзя сверять на точное равенство** — ни с отчётностью, ни
   между прогонами. Цифра идёт с допуском.
3. **S01 непригоден** (D4.2): коллизия `c_collateral_id`, 22% строк — не залог
   имущества. Покрытие 576% здесь — то же явление, что и 533% в D4.2, на
   подмножестве 90+.
4. **По S01 исключение поручительства и страховки не проконтролировано.**
   `c_collateral_type` — `varchar(100)`, сравнивается с `nvarchar`-литералом.
   Если совпадений нет, исключение молча не сработало и занизило недопокрытие
   по S01. На вывод это не влияет (S01 и так не используется), но контроль
   `GROUP BY c_collateral_type` нужен до того, как S01 когда-либо будет введён
   в оборот.
5. **`total_balance_debt` собран из разных слагаемых по источникам** (T15, P3):
   `la_account_1401` тождественно нулевой у всех четырёх, 1818/1838 нулевые у
   S03/S17. Межисточниковое суммирование экспозиции этим ограничено.

## 17. Проба P10 — `days_past_due` пуст у 88% остатка. H15 сузился до нижней границы

Повод: H15 дал по S02 ноль договоров 90+. Проверялись три версии — поле не
заполнено / поле обрезано сверху / книга правда чистая. Ответ оказался хуже
всех трёх, потому что он не про S02.

### 17.1 Поле не заполнено во ВСЕХ четырёх источниках

| источник | договоров в срезе | `days_past_due` заполнен | экспозиция | доля экспозиции БЕЗ DPD |
|---|---|---|---|---|
| S01 | 4 838 | 478 (**9,9%**) | 622,5 млрд ₸ | **91,1%** |
| S02 | 34 735 | **0 (0,0%)** | 2,0 млрд ₸ | **100,0%** |
| S03 | 254 338 | 53 592 (**21,1%**) | 831,2 млрд ₸ | **84,3%** |
| S17 | 90 597 | 10 939 (**12,1%**) | 121,2 млрд ₸ | **96,5%** |
| **итого** | **384 508** | **65 009 (16,9%)** | **1 577,0 млрд ₸** | **87,9%** |

По S02 поле пусто буквально: `MIN`, `MAX` — NULL, `COUNT(DISTINCT)` = 0.
Гипотеза «обрезано сверху» отпала у всех: максимумы 5 979 / 5 557 / 1 716 дней,
253–2 822 различных значения. Там, где поле заполнено, оно нормальное.

### 17.2 Что здесь НЕ доказано

NULL коррелирует с отсутствием просрочки: в корзине 1 доля NULL 96–98%, в
корзине 3 — 16–55%. То есть правдоподобно, что DPD проставляется только
просроченным, и тогда основная масса NULL — это здоровые договоры, а не потеря.

**Но одно другого не отменяет.** Даже если правило такое, поле не заполнено там,
где просрочка признана самим DWH (см. 17.3). Оба утверждения истинны
одновременно: поле триггерится просрочкой И неполно внутри просрочки.

Что именно значит NULL — вопрос к владельцу витрины, и его нужно задать прямо,
а не додумывать. До ответа `days_past_due` нельзя использовать как единственный
источник признака 90+.

### 17.3 `delinquency_bucket` показывает просрочку там, где DPD молчит

| источник | корзина 3/4 | из них **без DPD** | из них DPD > 90 |
|---|---|---|---|
| S01 | 918 | 534 | 289 |
| S02 | 2 010 | **2 010** | 0 |
| S03 | 49 682 | 8 115 | 35 664 |
| S17 | 10 460 | 2 453 | 7 153 |
| **итого** | **63 070** | **13 112** | **43 106** |

**13 112 договоров отнесены самим DWH к старшим корзинам просрочки и при этом
не имеют ни одного дня DPD.** Ни один DPD-сценарий их не видит — ни H15, ни
roll-rate H02, ни cure/re-default H03/H04, ни T13.

Это и есть ответ по S02: 2 010 договоров в корзине 3 при нуле по DPD. Книга
не чистая — молчит поле.

### 17.4 Заменить DPD на корзину нельзя — у корзины свой дефект

Домен `delinquency_bucket` **разный по источникам**: S01/S03 — {1,2,3,4},
S02/S17 — {1,2,3,NULL} (9 497 и 6 258 договоров с NULL-корзиной). Границы тоже
не совпадают: у S17 корзина 2 заканчивается ровно на 90 днях, у S03 в корзине 1
есть договор с DPD 98, в корзине 2 — восемь договоров с DPD 91.

И корзина 3 — не тождественно «90+»: в ней 91 договор S01, 5 888 S03 и 854 S17
имеют DPD ≤ 90.

Итог: **ни одно из двух полей не даёт признак 90+, сопоставимый между
источниками.** Это T19, подтверждённая на всём срезе, и это блокер приёмки, а
не методическое неудобство: регуляторная отчётность требует одного определения
на банк.

### 17.5 Что это делает с H15

Цифра §16 (18,80 млрд ₸ по S03+S17) верна для того, что измеряет: недопокрытие
среди договоров с заполненным DPD > 90. Она **не** является недопокрытием банка
по просрочке 90+. Как минимум 13 112 договоров в неё не вошли — на 30% больше,
чем она посчитала, и это нижняя оценка пропуска.

Моя формулировка «итог по пригодным источникам» была неверной: пригодность
проверялась по источникам, а ограничение проходит по **заполненности поля**
внутри каждого источника. Исправлено пометкой в §16.

Пересчёт по корзине даст вторую цифру, и она тоже не будет «правильной» — по
17.4. Правильный следующий шаг — не третья цифра, а вопрос владельцу витрины:
каким полем DWH считает 90+ и почему их два.

### 17.6 P10d — исключение по S01 РАБОТАЕТ, и оно решающее

Граница §16.5 п.4 закрыта: сравнение `varchar(100)` с `nvarchar`-литералом
совпадения находит.

| S01, тип обеспечения | строк | сумма | на одну штуку |
|---|---|---|---|
| Залог имущества | 7 713 | 1 615,7 млрд | 209,5 млн ₸ |
| **Поручительство** | 2 294 | **3 555,5 млрд** | 1 549,9 млн ₸ |
| Залог вклада | 453 | 79,8 млрд | 176,2 млн ₸ |
| **Страховой полис** | 32 | **89,5 млрд** | **2 795,8 млн ₸** |
| Заклад денег | 33 | **4 050 ₸** | **123 ₸** |

Исключаемое — **3 645,0 млрд из 5 340,5 млрд, то есть 68,3%** обеспечения S01.
Без этого исключения залог S01 был бы завышен втрое. Решение D4.2 подтверждено
на данных, а не на здравом смысле.

Попутно две аномалии значений: страховой полис в среднем 2,8 млрд ₸ за штуку и
«заклад денег» — 123 ₸ за штуку на 33 строки. Обе не проверялись отдельно.

### 17.7 У S03 и S17 тип обеспечения — константа `CAR`

Единственное значение на 103 659 и 16 657 строк. Латиницей, тогда как S01
использует русские термины: **общего справочника типов обеспечения нет**.

Средние правдоподобны (9,6 и 10,2 млн ₸ за объект — похоже на автомобиль),
поэтому «поле-заглушка» это или действительно моно-продуктовые автопортфели —
по этим данным не различается. Практическое следствие однозначно: **для S03 и
S17 отделить залог имущества от прочего обеспечения невозможно** — правило,
которое спасло S01, к ним неприменимо.

### 17.8 У S02 нет ни одной строки в `pledges`

S02 отсутствует в P10d целиком. Вместе с 17.1 это значит: у S02 нет ни DPD, ни
обеспечения. Ни один из четырёх кредитно-рисковых показателей по этому
источнику не строится.

Дополнительно: 34 735 договоров на 1,95 млрд ₸ — 56 тыс. ₸ средний остаток,
в 24 раза меньше S17. При том что в `loans` у S02 около 604 тыс. договоров
(L1/E-уровень), а H02d зафиксировал обрыв ряда на 163 936 договоров в 01.2026.
Похоже на усечённую загрузку, но как отдельная гипотеза не проверялось.

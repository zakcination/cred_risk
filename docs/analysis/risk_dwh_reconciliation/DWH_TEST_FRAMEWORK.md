# Framework тестирования DWH `Dictionaries.risk_analytics`

Документ по KPI **«Развитие DWH и контроль качества данных»**, период оценки — III квартал
2026 года. Закрывает пункты 1 и 2 KPI: **методология** и **подготовка тестирования**.
Пункты 3 и 4 — проведённый цикл и взаимодействие с БИТ — описаны в отчёте
`DWH_TEST_REPORT_C1.md`.

Framework не придуман заново. Он собран из правил, по которым тестирование уже велось
с июля 2026 года: каждое правило здесь подтверждено хотя бы одним случаем, когда его
нарушение стоило прогона или ложного вывода. Ссылки на такие случаи даны в тексте.

---

## 1. Объект и цель

**Объект.** Новая витрина рисков `Dictionaries.risk_analytics` (далее — март). Она
объединяет займы четырёх систем-источников:

| Код | Система | Таблицы старой ветки (эталон сравнения) |
|---|---|---|
| S01 | RS, розничное ядро | `PORTFOLIO_RS` |
| S02 | карты: Way4, SMARTCARD, Installment, kpk, Payda | `PORTFOLIO_CREDITCARDS_WAY4`, `_MIGR_WAY4`, `_SMART_CARD` |
| S03 | CrediLogic, основная выдача | `CL_PORTFOLIO_2` |
| S17 | Fenix | `PORTFOLIO_Fenix` |

Эталон — старая ветка `CL_PORTFOLIO.dbo`. Пока сверка не закрыта, она остаётся вторым
независимым измерением тех же займов.

**Цель.** Построить доказанную основу для перевода отчётности на март: для каждой таблицы —
подтверждённые ключи, гранулярность (grain), даты и формулы; для каждого поля — вердикт,
можно ли им пользоваться. Отчётность, построенная на этой основе, не должна требовать
повторного разбора марта.

**Условие, которое определяет весь метод.** Спецификации марта нет, автор недоступен.
Поэтому любое утверждение о марте доказывается **на данных**, а документы, названия колонок
и схемы используются только как гипотезы.

## 2. Принципы

| № | Принцип | Почему — случай из практики |
|---|---|---|
| **П1** | **Доказательство только на данных.** Имя колонки не определяет её смысл | `l_rate` оказалась названием кредитной программы, а не ставкой: 0 числовых значений из 8 259 299. `la_loan_id` по S03 даёт 0 совпадений со старой веткой |
| **П2** | **Три статуса вывода: подтверждено / открыто / опровергнуто.** Единый реестр — `FINDINGS.md`. Опровергнутое не удаляется: хранится прежняя формулировка и причина отзыва | повторно наступить на снятую ловушку легче, чем на новую |
| **П3** | **От фундамента к показателям.** Следующий уровень не проверяется, пока предыдущий не закрыт причиной, а не числом | сумма поверх размноженного JOIN выглядит как число, но числом не является |
| **П4** | **Без эталона вина не присваивается.** «Новая ветка выше» не значит «новая ветка неправа» | +30,6 млрд ₸ провизий S03: переоценивает март или недорезервирует старая ветка — без бухгалтерского эталона не решается |
| **П5** | **Каждая цифра воспроизводится вторым, независимо написанным запросом** | контроль периметра: два сценария независимо дают 8 259 299 строк |
| **П6** | **Дефект скрипта отделяется от дефекта марта** — до отправки в БИТ | прогон №1 послойной проверки дал шесть находок про скрипт, а не про март |
| **П7** | **Только чтение, только агрегаты.** Без ИИН, ФИО, номеров договоров в выводе | сценарий M12 печатал ФИО из поля группы — исправлен после прогона: вместо названия выводятся ранг и хеш |

## 3. Архитектура тестов

Тесты разделены по назначению. Каждый уровень отвечает на свой вопрос и не заменяет
другие.

| Уровень | Вопрос | Объём | Где |
|---|---|---|---|
| **Послойная проверка** | можно ли доверять таблице как основанию для следующей | 71 проверка в 14 слоях L0–L13 | `sql/risk_dwh_layered_check.sql` |
| **Сценарии аналитика** | справится ли март с реальными запросами аналитики | 100 сценариев в трёх уровнях сложности | `DWH_TEST_SCENARIOS.md`, `sql/DWH_SCENARIOS_*` |
| **Пробы** | какая из двух гипотез верна, если результат сценария неоднозначен | по одной пробе на вопрос; P1–P13 | `sql/DWH_PROBE_*` |
| **Кейс-прогоны** | воспроизводимое доказательство конкретного дефекта для БИТ | CASE_RUN 009–013 | `sql/CASE_RUN_*` |
| **Сверка со старой веткой** | кто из договоров потерялся и сходятся ли деньги | периметр, баланс, провизии, DPD по каждому источнику | `FINDINGS.md` §1–§6 |
| **Проверка полноты по плану счетов** | все ли счета займов входят в формулы | DQ-1…DQ-8 | `SCHETA_DQ.md` |

### 3.1 Послойная проверка: 14 слоёв

Слои идут в порядке зависимости: если нижний слой не прошёл, верхние всё равно
считаются, но помечаются «доверять нельзя».

| Слой | Что проверяется |
|---|---|
| L0 | схема и домены: типы ключей, словарь источников, выравнивание дат — до первого JOIN |
| L1 | `loans` — мастер-таблица: grain и уникальность ключа |
| L2 | `loans_active` — что считается живым договором |
| L3 | `loan_account` — деньги на отчётную дату, 25 счетов главной книги |
| L4 | `borrower` — клиент и ссылочная целостность |
| L5 | периметр старой и новой ветки: кто потерялся |
| L6 | баланс на совпавших договорах |
| L7 | провизии |
| L8 | DPD и 90+ |
| L9 | залоги |
| L10 | выбытие: списания, взыскание, внебаланс |
| L11 | график и платежи |
| L12 | периферийные таблицы: рейтинги, ставки, гарантии, кредитные линии, реструктуризации |
| L13 | итоговая витрина |

### 3.2 Сценарии аналитика: три уровня

| Уровень | Сценарии | Что проверяет |
|---|---|---|
| 1 — простой | E01–E35 | одна таблица: заполненность полей, домены значений, типы, NULL |
| 2 — средний | M01–M40 | связи и кардинальность: досье клиента, покрытие связей, дубли, реструктуризации, рейтинги, гарантии |
| 3 — сложный | H00–H25 | динамика и витрины: поколения, roll-rate, cure-rate, повторный дефолт, LTV, прогноз потока, резолюшн |

У каждого сценария указано не только «что посчитать», но и **на какой ловушке он
ломается**. Сценарий, который невозможно выполнить корректно из-за известного дефекта,
ценнее гладкого: он показывает границу пригодности марта.

## 4. Порядок проверки

Жёсткая последовательность. Переход к следующему шагу — только когда предыдущий закрыт
**причиной**, а не числом.

| Шаг | Что делается | Почему здесь |
|---|---|---|
| 0 | схема и типы ключей по живому аудиту `INFORMATION_SCHEMA` | до любого JOIN: `l_borrower_id varchar(255)` против `b_borrower_id bigint` |
| 1 | совместимость доменов источника | один ли словарь S01/S02/S03/S17 во всех таблицах |
| 2 | grain: сырые строки против различных ключей по источнику и дате | размножение строк надо поймать до сумм |
| 3 | выбор ключа **по покрытию**, все кандидаты | номер договора не глобален: 9 659 коллизий между источниками |
| 4 | выравнивание дат к началу месяца | даты обеих веток — первое число месяца |
| 5 | периметр: совпавшие / только в старой / только в новой, с разбивкой по статусу | «нет договора» и «сумма другая» — разные дефекты |
| 6 | остатки на совпавших договорах | сначала счета, потом производные |
| 7 | экономическое содержание: баланс и движение | до вывода о вине одной из веток |
| 8 | провизии, DPD, 90+ | риск-параметры двигают регуляторную цифру |
| 9 | выбытие: списания, взыскание, внебаланс | «нет строки» здесь легитимно для части источников |

## 5. Критерии прохождения и вердикты

**Сценарий пройден**, если выполнены все четыре условия, а не если запрос вернул строки:

1. использован канонический ключ (`*_gid = l_gid` и `*_source = l_source`), а не поле
   с похожим названием;
2. NULL отделён от нуля и от «записи нет»;
3. число воспроизводится вторым, независимо написанным запросом;
4. если источники ведут себя по-разному, это видно в разрезе, а не усреднено.

**Вердикт по выводу** — один из трёх: подтверждено, открыто, опровергнуто. **Вердикт
по полю** в реестре полей — пригодно, ловушка, непригодно, отозвано.

**Контрольная колонка входит в вердикт.** Если сценарий печатает долю неизвестного,
эта доля должна влиять на вердикт, а не стоять рядом с ним. Урок из практики: доля пустых
DPD была напечатана в прогоне сценариев, но прочитана только после отдельной пробы.

## 6. Библиотека ловушек

48 ловушек T1–T48 в `DWH_TEST_SCENARIOS.md` — конкретные места, где март даёт неверный
ответ на корректно заданный вопрос. Ниже — общие классы, из которых они состоят.

| Класс | Пример |
|---|---|
| имя колонки ≠ смысл | `l_rate` — название программы; `la_loan_id` не работает как ключ S03 |
| NULL ≠ 0 | `days_past_due` пуст у 87,9 % экспозиции: при NULL = 0 доля 90+ — 14 %, при NULL = «неизвестно» — 67 % |
| INNER JOIN не видит спорных договоров | провизии и DPD на внутреннем соединении не видят договоров, которые есть только в одной ветке |
| тройной ноль = выбитый ключ | ноль по трём таблицам перепроверяется другим ключом до вывода «отсутствует» |
| промежуточная группировка превращает проверку в тавтологию | `GROUP BY` по ключу до подсчёта дублей по тому же ключу |
| исчезнувший срез | жёсткая дата `2026-07-01` дала 0 строк: снимка больше нет |
| присутствие в таблице ≠ живой договор | нужны статус и движение остатка |

## 7. Правила SQL

Действуют во всех скриптах тестирования.

- Только `SELECT`; временные объекты — только `#temp`, с префиксом файла.
- `MAXDOP 1` на тяжёлых запросах.
- Только трёхчастные имена `[Dictionaries].[risk_analytics].[X]`. Двухчастное имя
  разрешается в текущую базу сессии, а аудит схемы в чужой базе возвращает 0 строк
  без ошибки.
- Имена колонок — только из живого аудита, не из BI-канваса: канвас разошёлся с базой
  минимум по трём полям и стоил трёх прогонов.
- Нормализация ключа — только разово для аудита, не в каждом JOIN: иначе JOIN перестаёт
  использовать индекс и зависает.
- `CROSS APPLY (VALUES …)` — после фильтра, а не до: иначе размножается весь портфель.
- Даты, допуски и источники — параметры, а не значения в теле запроса.
- Сначала агрегат, потом детализация; без `SELECT *`.

## 8. Подготовка цикла тестирования

Чек-лист перед каждым прогоном.

| № | Шаг | Что предотвращает |
|---|---|---|
| 1 | Батч 0 — аудит схемы того объекта, к которому идёт запрос, отделён `GO` | запрос по несуществующей колонке; `loans_active` уже таблицы `loans` |
| 2 | Отчётная дата определяется как последняя дата **каждого** источника, а не общая | S03 загружен на месяц вперёд: общая дата показала бы только S03 |
| 3 | Контроль периметра двумя независимыми итогами | нули в результате — это нули данных, а не потерянный фильтр |
| 4 | Статическая предпроверка скрипта до запуска | предпроверка перед прогоном №2 нашла десять дефектов текста, три из них давали ложно-зелёные вердикты |
| 5 | Скрипт разбит на независимые `GO`-батчи, временные таблицы именованы с префиксом | падение одного батча не валит соседние |
| 6 | Самопроверка скрипта и результата до отправки: ключ, знаменатель, PII | самопроверка уровня 3 до передачи нашла три ошибки: размножение по снимкам, `CROSS JOIN` до фильтра даты, переоценённую формулировку |
| 7 | Агрегаты прогона сохраняются на своей стороне | март хранит историю только одной таблицы из четырнадцати: после следующей загрузки цифру не воспроизвести |

## 9. Разбор результатов и передача дефектов в БИТ

**Перед письмом в БИТ — пять проверок.** Полная версия — `DEFECT_REPORT_GUIDE.md`.

1. Ключ канонический и доказан покрытием, а не именем колонки.
2. Периметр проверен: дефект не объясняется датой среза или фильтром.
3. Величина измерена в деньгах и числе договоров, по каждому источнику.
4. Есть воспроизводимый скрипт, который БИТ может запустить у себя.
5. Дефект скрипта исключён: вывод выдержал независимую перепроверку.

**Структура письма:** что обнаружено; как воспроизвести; величина; что нужно от
получателя; что не утверждается. Письмо привязывается к дате среза, потому что март
перезаписывается без истории.

**Учёт.** Инвентарь «отправлено / не отправлено» и черновики писем ведутся
в `DEFECT_REPORT_GUIDE.md`.

## 12. Периодичность

- **Регрессионный прогон** послойной проверки — после каждого изменения марта, о котором
  сообщает БИТ, и перед переключением любого отчёта на март.
- **Повторная проверка отправленного дефекта** — после ответа БИТ: подтверждение
  исправления письмом, а не молчанием.
- **Реестры полей и связей** обновляются по каждому прогону, в котором появился новый факт.

Периодичность — предложение этого документа, она не утверждена.

---

## 13. Ограничения

- Framework проверяет март против старой ветки и против самого себя. **Бухгалтерского
  эталона в нём нет**: где ветки расходятся, он показывает расхождение, но не решает,
  какая из них права.
- Март хранит историю только одной таблицы из четырнадцати. Динамику можно проверить
  только по ней.
- Framework не проверяет производительность марта и регламент загрузки — только
  содержание данных.

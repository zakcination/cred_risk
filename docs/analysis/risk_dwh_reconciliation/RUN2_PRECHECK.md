## П2-1. Пустая база даёт `PASS` — и это главный дефект списка

Почти каждая проверка L0–L6 отбирает по `= @AsOf` и считает **разность**:

```sql
-- L1.1, строка 446
N'excess_raw_rows', SUM(rows_in_group) - COUNT_BIG(*), N'0',
CASE WHEN SUM(rows_in_group) - COUNT_BIG(*) > 0 THEN N'FAIL' ELSE N'PASS' END, 1,
```

Если на `@AsOf` строк нет вовсе, `#l1` пуст, агрегат по пустому множеству не даёт ни одной
группы — строка результата **не появляется**, а там, где `GROUP BY` отсутствует (L4.3, L4.4,
L0.6), `SUM(...)` по пустому множеству даёт `NULL`, и ветвь `> 0` ложна ⇒ **`PASS`**.

То же по конструкции у всех «не найдено = 0»: `L2.2`, `L3.2`, `L3.3`, `L4.1`, `L4.2`.
`NOT EXISTS` по пустому левому множеству даёт ноль строк ⇒ ноль расхождений ⇒ `PASS`.

**Почему это не теоретическая придирка.** Контур сам доказал два сценария пустого среза:
`S03 загружен на месяц вперёд` (проба P1) и обрыв фев-2026 у `S02` (счета 185 828 → 30 973).
При `@AsOf = '2026-07-01'` достаточно, чтобы одна таблица не имела этой даты, — и слой
отрапортует «чисто».

Параметр `@MinBase` объявлен в §0 (строка 172) ровно под это — «ниже этой базы доля шум,
а не метрика», — но применяется **только дважды, и оба раза внутри L8**: `L8.3` (строка 1311)
и `L8.8` (строка 1433). Вердикт `NO_BASE` существует в схеме `##RDW_RESULTS` и в §REPORT,
но в слоях L0–L7 и L9–L13 не выставляется ни разу.

**Что делать:** перед каждым слоем печатать базу (`COUNT` строк, попавших под фильтр) и
выставлять `NO_BASE` вместо `PASS`, когда база нулевая. `L2.2b` такую строку уже печатает
для активного периметра — приём есть, он просто не распространён на остальные слои.

## П2-2. `L0.4` не видит `source IS NULL`

```sql
-- строки 360-363
FROM #srcdom s
WHERE s.src NOT IN (N'S01',N'S02',N'S03',N'S17')
GROUP BY s.src
HAVING SUM(s.n) > 0
```

`NULL NOT IN (...)` даёт `UNKNOWN`, а не `TRUE`, — строка отсеивается `WHERE`. Явная
ветвь `PASS` ниже (строка 367) использует **тот же предикат**:

```sql
IF NOT EXISTS (SELECT 1 FROM #srcdom WHERE src NOT IN (N'S01',N'S02',N'S03',N'S17'))
```

Значит таблица, где часть строк имеет `source = NULL`, даёт `PASS` с формулировкой
«домен source единый во всех проверенных таблицах — подтверждает предпосылку всех
пер-сорсных сверок ниже». Предпосылка при этом ложна: строки с `NULL` выпадут из каждой
группировки `GROUP BY source` и будут выглядеть как отсутствие данных.

`L1.4` ловит `l_source IS NULL`, но только в `loans` и только на своём срезе; для
`loan_account`, `pledges`, `borrower` такой проверки нет.

**Что делать:** `WHERE s.src IS NULL OR s.src NOT IN (…)`, отдельной метрикой
`rows_with_null_source`.

## П2-3. `L0.2` объявляет совместимость типов, сравнив только имя типа

`#keytypes` (строка 300) забирает три колонки:

```sql
SELECT TABLE_NAME, COLUMN_NAME, DATA_TYPE, CHARACTER_MAXIMUM_LENGTH, NUMERIC_PRECISION
```

а сравнение (строка 313) использует одну:

```sql
CASE WHEN a.DATA_TYPE = b.DATA_TYPE THEN 1 ELSE 0 END
```

`CHARACTER_MAXIMUM_LENGTH` и `NUMERIC_PRECISION` не участвуют нигде. `varchar(50)` против
`varchar(255)` даёт `PASS` при `is_gate = 1`, хотя усечение на сравнении — ровно та
семантика, от которой проверка защищает. Показательно, что обе колонки в выборке есть:
намерение было, реализация до него не дошла.

## П2-4. `@DpdOffByOne` объявлен, задокументирован и не применён ни разу

```sql
-- строка 173
DECLARE @DpdOffByOne int = 1;   -- документированная off-by-one: old = new − 1
```

Единственное вхождение во всём файле. При этом матрица 90+ (`L8.4`) и обе односторонние
проверки (`L8.5`, `L8.6`) сравнивают **сырые** значения с одним порогом:

```sql
-- строки 1353-1355, 1369-1370
WHEN old_dpd_max > @NinetyPlus THEN N'old:90+' ELSE N'old:≤90'
WHEN new_dpd_max > @NinetyPlus THEN N'new:90+' ELSE N'new:≤90'
```

Если правило `old = new − 1` держится хотя бы частично — а `L8.3` фиксирует совпадение
61–99 % по источникам, — то договоры с `new_dpd_max = 91` дают `old_dpd_max = 90`, то есть
`new:90+` против `old:≤90`. Это **систематическая полоса ложных ONLY_NEW_90 шириной ровно
в один день просрочки**, и она попадёт в отчёт как расхождение марта.

Оговорка, которая важнее находки: применять сдвиг «на всякий случай» **нельзя** — `L8.3`
показывает, что правило не универсально (S03 не подтвердилось вовсе). Правильная правка —
не сдвигать, а печатать матрицу дважды, со сдвигом и без, и смотреть, какая полоса
схлопывается. Иначе одна необоснованная поправка заменит другую.

Вторая оговорка, снижающая вес находки: `L8.7` (строка 1410) уже печатает договоры
**ровно на `DPD = 90`** по новой стороне — то есть граница как таковая не забыта.
Но `L8.7` считает одну сторону и не отвечает на вопрос, сколько из них имеют
`old_dpd_max = 89` и потому попали в расхождение искусственно. Дефект — не в отсутствии
внимания к границе, а в том, что объявленный сдвиг не участвует в сравнении.

## П2-5. `@ValueRatioFlag` объявлен дважды, второй раз — константой

```sql
-- §0, строка 175
DECLARE @ValueRatioFlag decimal(18,4) = 10.0;
-- L9, строка 1465 — новый батч после GO
DECLARE @ValueRatioFlag decimal(18,4) = 10.0;
```

Все прочие параметры в слоях читаются из `##RDW_PARAMS` (`@AsOf`, `@Tolerance`,
`@NinetyPlus`, `@MinBase`, `@SourceFilter`) — потому что локальные переменные не переживают
`GO`. Здесь вместо чтения повторён литерал. Следствие: правка `@ValueRatioFlag` в §0
на проверку `L9.5` **не влияет**, а §Отчёт 4 печатает параметры прогона из `##RDW_PARAMS`,
то есть покажет изменённое значение, которого проверка не видела. Прямое нарушение правила
контура «tolerance / даты / source — параметры, не хардкод в теле».

Заодно: `@ValueRatioFlag` вообще не попадает в `##RDW_PARAMS` (см. `INSERT` на строках
198–209) — то есть в отчёте о параметрах его нет, а в теле он есть.

## П2-7. `@SourceFilter` не действует в `L7.3` и `L8.1`

Параметр объявляется в батчах L0–L5 (строки 428, 522, 620, 759, 874) и применяется
одиннадцать раз. В батчах **L7 и L8 он не объявляется вовсе**, и обращения к
`loan_account` идут без него:

```sql
-- L7.3, строки 1212-1214
FROM [Dictionaries].[risk_analytics].[loan_account]
WHERE la_reporting_date = @AsOf7
GROUP BY la_source
-- L8.1, строки 1266-1268 — то же самое
```

Обе проверки группируют по `la_source` и печатают строку на каждый источник. В режиме
«один источник за раз» — который шапка скрипта прямо рекомендует для тяжёлого S02 —
отчёт получит по L1–L5 один источник, а по L7.3 и L8.1 все четыре, без какой-либо пометки
о разном периметре. И наоборот: самая тяжёлая таблица сканируется целиком именно в том
режиме, который заведён ради снижения нагрузки.

Обе проверки переписывались 04.08 в рамках оптимизации `UNION ALL` → `CROSS APPLY VALUES`.
Правка описана в шапке как «форма отчёта не меняется»; фильтр источника при этом пропал.
Сама оптимизация корректна: `CROSS APPLY` стоит **после** агрегата, размножаются считанные
строки на источник, а не портфель, — то есть правило контура здесь соблюдено.

## П2-8. `L0.5` — гейт по выравниванию дат покрывает две таблицы из пяти

Проверяются `loans` и `loan_account` (строки 379–383). Не проверяются `loans_active`,
`pledges`, `borrower` — при том что все три фильтруются по `= @AsOf` ниже

`PASS` при пустой левой стороне — в зависимости от того, какая сторона опустела.

## П2-9. Имена `#temp` без префикса файла — единственный дефект, способный уронить прогон

В файле используются `#exp`, `#keytypes`, `#srcdom`, `#dates`, `#l1`, `#act`, `#la`,
`#borrower_keys`, `#rs_keys`, `#gatefail`. Правило контура сформулировано дословно:

> Имена `#temp` — с префиксом файла (`#hb_acct`, а не `#acct`). SQL Server связывает
> ссылки на `#temp` при КОМПИЛЯЦИИ батча, а `IF OBJECT_ID(…) DROP` — во время
> ВЫПОЛНЕНИЯ. Одноимённая таблица с ДРУГИМ набором колонок, оставшаяся от прерванного
> скрипта, даёт `Msg 207`. Так упал L2B 09.08 после падения L2A.

`#act` и `#la` — те самые имена, которые правило приводит как пример. В наборе контура
`#acct` есть и в `DWH_SCENARIOS_L3A_HARD`, и в `DWH_PROBE_H15_STANDALONE` (там уже
переименован в `#h15_*` после падения). Прогон №2 планируется запускать **по слоям** —
это режим, в котором остаток от прерванного соседнего скрипта переживает в tempdb
дольше всего.

Правка механическая: префикс `#rdw_` на все десять имён.

## П2-10. Недоступность cross-db обнуляет доверие ко всем 14 слоям

`L0.1` помечает `is_gate = 1` для каждой из 29 ожидаемых таблиц, включая 10 таблиц
`CL_PORTFOLIO` (строки 269–278). §REPORT берёт минимальный слой с проваленным гейтом:

```sql
-- строки 1844-1847
SELECT MIN(layer_no) AS first_failed_gate_layer
FROM ##RDW_RESULTS WHERE is_gate = 1 AND verdict = N'FAIL';
```

Шапка скрипта сама говорит: «Cross-db работает только на одном инстансе. Если падает —
это находка, а не ошибка скрипта». Но если cross-db недоступен, десять строк `L0.1`
дают `FAIL` с `is_gate = 1`, `first_failed_gate_layer = 0`, и **каждый** слой печатает
«ДОВЕРЯТЬ НЕЛЬЗЯ — провален гейт L0», включая L1–L4 и L9, которые старой ветки
не касаются вовсе и остаются полностью валидными.

Отчёт в этом сценарии не читается: находка про инфраструктуру маскирует все результаты
по новой ветке. Разделить просто — гейт по таблицам `Dictionaries` и гейт по таблицам
`CL_PORTFOLIO` должны быть разными, и второй обязан обнулять доверие только к слоям,
которые сравнивают с эталоном (L5–L8, L10.3).

## Что этот разбор проверить не мог

- **Всё, что видно только на данных.** Класс из шести дефектов прогона №1 сюда не входит
  по построению.
- **Имена колонок.** Каждое имя в скрипте взято на веру; живой аудит `INFORMATION_SCHEMA`
  делает сам скрипт в `L0.1` / `L0.2`. Правило контура «имена колонок — только из живого
  аудита» здесь соблюсти нечем: базы у меня нет.
- **Стоимость планов.** Зависание `H15` 09.08 не поймало даже само-ревью автора —
  «проверялась корректность результата, не стоимость плана». Здесь то же ограничение.
- **L9–L12 разобраны выборочно** — по классам дефектов (параметры, фильтры, `#temp`,
  границы), а не построчно. Полный построчный разбор этих четырёх слоёв не делался.

## Порядок действий, предлагаемый до прогона №2

   рискует дать `PASS` там, где данных просто нет.
2. **П2-9** — префикс `#rdw_`. Единственная правка, которая может отменить прогон целиком.
3. **П2-1, П2-2, П2-3, П2-8** — ложно-зелёные вердикты. Пока они не сняты, `PASS`
   в отчёте прогона №2 не является утверждением.
4. **П2-7, П2-5, П2-6** — параметры и периметр; не искажают числа, искажают их чтение.
5. **П2-4 и П2-10** — правки отчётной логики, обе спорные по существу. Обсуждать до,
   а не молча вносить.

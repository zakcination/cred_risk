# CLAUDE.md — Risk DWH Reconciliation (БРМ, Eurasian Bank)

## Задача проекта
Реверс-инжиниринг и верификация нового DWH-марта **`Dictionaries.risk_analytics`**
против старой ветки **`CL_PORTFOLIO.dbo`**, чтобы построить **undeniable foundation**:
подтверждённые ключи, grain, даты, формулы — «мосты доверия» между таблицами, по которым
можно гонять данные и проверять гипотезы, зная что связки и суммы верны.
Автор марта недоступен, спецификации нет → всё доказывается **на данных**, не из документов.
Цель — перенос всех бизнес-процессов на новый DWH + помощь команде с table definitions,
JOIN'ами и формулами для отчётности.

Работа ведётся с двух сторон: **Sailau** (риск-параметры: provisions/DPD/90+) и
**Miras** (фундамент ключей + валентность + спорные бакеты). Файл `FINDINGS.md` —
это ground truth. **Читай FINDINGS.md первым.**

## Правила SQL-движка (НЕ нарушать)
- **Read-only.** Только SELECT. Запрещено: INSERT/UPDATE/DELETE/MERGE/DROP/ALTER
  постоянных объектов. Только `#temp` таблицы.
- **MAXDOP 1** на тяжёлых запросах (контроль tempdb/нагрузки).
- **PII не выводить:** ИИН/ФИО/номера договоров/IBAN — не в результат. Только агрегаты.
- **tolerance/даты/source — параметры**, не хардкод в теле.
- **Нормализацию НЕ вшивать в JOIN.** Доказано (M): сырой ключ = нормализованный
  (259 905 = 259 905). `UPPER(LTRIM(RTRIM()))` на обеих сторонах JOIN на большом
  наборе делает JOIN non-sargable → зависает. Нормализация — только для разового
  аудита «изменила бы что-то нормализация», не в каждый JOIN.
- **Только трёхчастные имена:** `[Dictionaries].[risk_analytics].[X]`, не
  `[risk_analytics].[X]`. Двухчастное имя резолвится в ТЕКУЩУЮ БД сессии, а
  подключение по умолчанию — `CL_PORTFOLIO`. Особо опасен `INFORMATION_SCHEMA`:
  в чужой БД он вернёт **0 строк без ошибки**, то есть аудит схемы «отработает»
  и ничего не покажет. Пишется `[Dictionaries].INFORMATION_SCHEMA.COLUMNS`.
- **Имена колонок — только из живого аудита, не из BI-канваса.** Канвас от
  30.07 разошёлся с базой минимум по трём полям и стоил трёх прогонов подряд
  (09.08). Любой скрипт на неподтверждённом имени начинается с батча-0
  `INFORMATION_SCHEMA`, отделённого `GO`, и аудит проверяет **тот объект, к
  которому идёт запрос**: `loans_active` — вьюха УЖЕ таблицы `loans`
  (нет `l_segment`, `l_financial_consultant`), см. FINDINGS §15.
- **В T-SQL нет булева типа.** `(a <= 1) <> (b <= 1)` даёт `Msg 102`. Признак
  разворачивать через `CASE … THEN 1 ELSE 0 END`.
- Сначала агрегат, потом детализация. Не `SELECT *`. Не FORMAT на больших выборках.

## Жёсткий порядок проверки (spiral — ловить рано, углубляться постепенно)
0. Схема+типы ключей (INFORMATION_SCHEMA) — ДО любых JOIN.
1. Совместимость доменов `source` (S01/S02/S03/S17 — один словарь, подтверждено).
2. Grain: `raw_rows vs distinct_key` по (source, date) — размножение до сумм.
3. Выбор ключа **по покрытию** — тестировать всех кандидатов, не верить имени колонки.
4. Выравнивание дат к month-start (…-01).
5. Периметр FULL OUTER → bucket-и (MATCHED/ONLY_OLD/ONLY_NEW), разбивка по статусу.
6. Остатки на MATCHED (сырые счета → производные).
7. Экономическое содержание (баланс+движение) — ДО вывода о вине ветки.
8. Provisions + DPD + 90+ (риск-параметры — двигают регуляторную цифру).
9. Resolution-пайплайн (writeoff/collections/Offbalance/…).
**Правило перехода:** не углубляться, пока предыдущий виток не закрыт ПРИЧИНОЙ, а не числом.

## Антипаттерны (уже стоили времени в этой сессии)
- **Имя колонки ≠ семантика.** `la_loan_id` matched 0 для S03 несмотря на имя.
  Product-поля S02 = NULL. Всегда проверять значениями, не именем.
- **Presence-in-table ≠ живой договор.** Нужен status + balance movement.
- **NULL ≠ 0.** `SUM(a+b)` обнуляется на NULL без COALESCE; но COALESCE прячет
  «счёт реально отсутствует». `NULL days_past_due` ≠ отсутствие просрочки.
- **INNER JOIN слеп к спорным бакетам.** Provisions/DPD на INNER не видят ONLY_OLD/ONLY_NEW.
- **Валентность:** «новая выше» ≠ «новая неправа». Может старая недорезервирует.
  Не присваивать вину без эталона (бух/IFRS 9).
- **Тройной ноль по трём таблицам = подпись выбитого ключа**, не реального отсутствия.
  Перепроверить ключ (у нас: ре-ключ по gid) прежде чем писать «отсутствует».
- **Паразитный `GROUP BY` перед подсчётом дублей = тавтология, не проверка.** Если промежуточный
  `GROUP BY (source, key)` схлопывает именно ту размерность, дубли по которой проверяются, то
  внешний `COUNT(*) = COUNT(DISTINCT key)` гарантированно верен КОНСТРУКЦИЕЙ запроса — подзапрос
  физически не может дать больше одной строки на ключ, сколько бы сырых дублей ни было в
  источнике. Стоило времени 17.07 (grain `loans`, PR #14 → отозван). Проверять дубли на сыром
  уровне: `SUM(count-в-группе)` против `COUNT(*)`-групп, не `COUNT(*)` над уже сгруппированным.

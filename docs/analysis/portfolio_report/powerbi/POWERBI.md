## Чем Power BI отличается от прежнего Excel

В Excel раскладка была данными: блок на показатель, строки — иерархия
(обеспеченный / необеспеченный → денежный / товарный → продукт), 12 месяцев в столбцах.

**В Power BI раскладка — это визуал.** Данные лежат длинной таблицей
`месяц × источник × показатели`, а матрица сама разворачивает месяцы в столбцы
и иерархию в строки с раскрытием «+». Поэтому спираль не требует перестраивать
модель: на каждом витке к измерению добавляется колонка, и матрица получает
ещё один уровень раскрытия.

## Модель

| Таблица | Зерно | Откуда | Суммируется |
|---|---|---|---|
| `fact_flow` | месяц × источник × продукт | `PBI_fact_flow.sql` | по месяцам, источникам, продуктам — да |
| `fact_stock` | месяц × источник × продукт | `PBI_fact_stock.sql` | по источникам и продуктам — да, **кроме заёмщиков**; по месяцам — **нет** |
| `fact_borrowers` | месяц × источник | `PBI_fact_borrowers.sql` | нет — заёмщики уровня источника |
| `dim_month` | месяц | DAX, из фактов | — |
| `dim_source` | источник | DAX, четыре строки | — |
| `dim_product` | продукт | DAX, таблица ниже | — |

Связи: `dim_month[Date]` 1 → * `month_start` всех трёх фактов; `dim_source[l_source]` 1 → *
`l_source` всех трёх; `dim_product[product_key]` 1 → * `fact_flow[product_key]`,
`fact_stock[product_key]`. С `fact_borrowers` у `dim_product` связи нет — намеренно.
Направление фильтра — одностороннее, от измерения к факту.

**Окно — 24 месяца, на экране — 12.** Вторые двенадцать нужны только для сравнения
«год к году». По запасу глубина ограничена историей `loan_account`: по S01 срезы
начинаются с 2025-01-01, поэтому «год к году» для запаса считается не на всех месяцах.

**Строка месяца M в `fact_stock` — это срез на 1-е число месяца M+1**, то есть запас
на конец месяца. Так запас включает выдачи месяца, и поток с запасом в одной строке
сходятся (`REPORT_STRUCTURE.md`).

### Подключение

Получить данные → SQL Server → база `Dictionaries` → Дополнительные параметры →
Инструкция SQL → вставить файл целиком. Режим **Импорт**. DirectQuery не подойдёт:
запросы используют CTE и `OPTION (MAXDOP 1)`, а DirectQuery оборачивает запрос
в подзапрос и принимает ни то ни другое.

До первого подключения — один раз `PBI_0_preflight.sql`.

## Измерения (DAX)

```dax
dim_source =
DATATABLE (
    "l_source", STRING, "Источник", STRING, "Порядок", INTEGER,
    {
        { "S01", "RS",         1 },
        { "S02", "Карты",      2 },
        { "S03", "CrediLogic", 3 },
        { "S17", "Fenix",      4 }
    }
)

dim_month =
VAR _mn = MIN ( MIN ( fact_flow[month_start] ), MIN ( fact_stock[month_start] ) )
VAR _mx = MAX ( MAX ( fact_flow[month_start] ), MAX ( fact_stock[month_start] ) )
RETURN
    ADDCOLUMNS (
        FILTER ( CALENDAR ( _mn, _mx ), DAY ( [Date] ) = 1 ),
        "month_idx", YEAR ( [Date] ) * 12 + MONTH ( [Date] ),
        "Месяц",     FORMAT ( [Date], "yyyy-MM" )
    )

-- вычисляемый столбец dim_month: фильтр страниц на последние 12
Последние 12 = dim_month[month_idx] > MAX ( dim_month[month_idx] ) - 12
```

`dim_source[Источник]` сортировать по `dim_source[Порядок]`.

## Меры (DAX)

### Поток — разделы 2-1 и 2-3

Складываются по месяцам и источникам без оговорок.

```dax
Объём выдач                    = SUM ( fact_flow[issued_amount] )
Количество выдач               = SUM ( fact_flow[issued_cnt] )
в т.ч. карт с лимитом          = SUM ( fact_flow[card_limit_pos_cnt] )   -- только S02; канон — PBI_model.dax
Средняя сумма выдачи           = DIVIDE ( [Объём выдач], SUM ( fact_flow[issued_cnt_amount_pos] ) )
Установлено лимитов по картам  = SUM ( fact_flow[card_limit_amount] )
Срок по договору, мес          = DIVIDE ( SUM ( fact_flow[term_sum] ), SUM ( fact_flow[term_cnt] ) )
Полностью погашено =
SUM ( fact_flow[closed_cnt] ) - SUM ( fact_flow[closed_overdue_cnt] )

Закрыто с просрочкой на начало месяца = SUM ( fact_flow[closed_overdue_cnt] )

в т.ч. досрочно =
SUM ( fact_flow[closed_early_cnt] ) - SUM ( fact_flow[closed_overdue_early_cnt] )

Доля досрочных =
DIVIDE (
    [в т.ч. досрочно],
    SUM ( fact_flow[closed_cnt_sched] ) - SUM ( fact_flow[closed_overdue_sched_cnt] )
)

Фактический срок, мес =
DIVIDE (
    SUM ( fact_flow[closed_days_sum] ) - SUM ( fact_flow[closed_overdue_days_sum] ),
    SUM ( fact_flow[closed_days_cnt] ) - SUM ( fact_flow[closed_overdue_days_cnt] )
) / 30.4375

S17 Т (сноска) = SUM ( fact_flow[closed_t_cnt] )
```

**Почему «полностью погашено» — без договоров, просроченных на начало месяца (Р-4).**
Статус «Закрыт» не отличает погашение от выбытия. У S17 в декабре 2025 им закрыто
35 679 договоров, и 86,2 % из них на 1-е число были просрочены — против 8–10 % в
обычные месяцы; 55 % закрыто одним днём (`RPT_G`, блок 1). Это выбытие портфелем.
Признак «просрочен на начало месяца» отделяет его без порогов и без ручного списка
месяцев. Цена — в обычные месяцы около 8 % настоящих погашений (заёмщик погасил
просрочку и закрыл договор) уходят во вторую строку. Они не теряются, а видны
отдельно: **«Закрыто с просрочкой на начало месяца»**.

**Принято по умолчанию, меняется одной строкой.** Вернуть прежнее определение —
убрать вычитание `closed_overdue_*` в четырёх мерах.

Признак есть только с 01.2025 — раньше срезов `loan_account` нет, и закрытия
09–12.2024 целиком попадают в «полностью погашено». На экранные 12 месяцев это
не влияет, на «год к году» для 09–12.2025 — влияет.

Знаменатель доли досрочных — только погашения, у которых **есть** плановая дата.
У карт её нет, и с ними доля занижалась бы на весь объём карточных закрытий.

### Запас и риск — разделы 3, 4-1 ③, 5

**Запас по месяцам не складывается.** В итоговом столбце матрицы за год
остаток должен быть остатком на последний месяц, а не суммой двенадцати.
Все меры запаса привязаны к одному якорю — последнему месяцу, где есть остаток.

```dax
_Остаток (сумма) = SUM ( fact_stock[balance] )

Общий остаток =
CALCULATE ( [_Остаток (сумма)], LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] ) )

Договоров с остатком =
CALCULATE ( SUM ( fact_stock[contracts_with_balance] ),
            LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] ) )

Просроченная задолженность =
CALCULATE ( SUM ( fact_stock[overdue_principal] ),
            LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] ) )

Управленческий уровень просрочки =
DIVIDE (
    CALCULATE ( SUM ( fact_stock[balance_of_overdue] ),
                LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] ) ),
    [Общий остаток]
)

Провизии =
CALCULATE ( SUM ( fact_stock[provisions] ),
            LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] ) )

Покрытие провизиями = DIVIDE ( [Провизии], [Общий остаток] )

Счёт 1484 (вне формулы) =
CALCULATE ( SUM ( fact_stock[acc_1484] ), LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] ) )

Счёт 1485 (вне формулы) =
CALCULATE ( SUM ( fact_stock[acc_1485] ), LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] ) )
```

**Провизии с июня 2026 неполны (Р-5, `RPT_G` блок 2).** На S03 в июне 2026 появились
с нуля счета **1484 (+29,6 млрд)** и **1485 (+29,1 млрд)**; одновременно `1428`, `1860`
и `1434` упали сверх обычного сокращения. Это перенос остатков, а не высвобождение.
Формула `1428 + 1845 + 18771` его не видит — поэтому «покрытие» после мая 2026
выглядит упавшим с 9,2 % до 7,1 %, чего на деле не было.

Что такое 1484 и 1485 по плану счетов, **не установлено**: в `risk_analytics_data_model.md`
их нет.

**Итоговое совпадение оказалось обманчивым (витрина, разрез по продуктам, 24.09.2026).**
По S03 в целом `1428` за вычетом обычного сокращения потерял ≈ 29,7 млрд, а `1484`
получил 29,59 — это выглядело как перенос провизий. По продуктам так не выходит:
у новых авто `1484` на 7,5 млрд **больше** падения провизий, у всех остальных
продуктов — меньше. Оба счёта сидят на одном продукте:

| | доля новых авто |
|---|---|
| остаток S03 | 65,2 % |
| `1484` | 76,5 % |
| **`1485`** | **97,8 %** |

`1485` — практически счёт одних новых автокредитов. В тот же месяц упали `1434` и
`1860` — по таблице `risk_analytics_data_model.md` это дисконты и комиссии. Вопрос
бухгалтерии: не переехали ли туда дисконты и комиссии по новым авто, и что тогда
лежит на `1484`. **До ответа ни один из счетов в провизии не включать** — стоят
отдельными мерами. Если ответ подтвердит, что `1484` — провизии, включить одной строкой:

```dax
-- только после подтверждения, что 1484 — провизии
Провизии =
CALCULATE ( SUM ( fact_stock[provisions] ) + SUM ( fact_stock[acc_1484] ),
            LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] ) )
```

**Заёмщики между источниками не складываются.** Номер заёмщика системный:
один человек в RS и в Fenix — два разных `l_borrower_id`. Сумма по источникам
завысит число людей. Мера показывает значение только внутри одного источника;
на итоге банка она пустая, пока нет сквозного подсчёта через ИИН (виток 2+).

С витка 2 заёмщики не складываются и **между продуктами**: у одного человека бывает
и POS, и зарплатный кредит. Поэтому значение есть только на двух уровнях — у одного
продукта (из `fact_stock`) и у источника целиком (из `fact_borrowers`). На группах
продуктов и на итоге банка мера пустая.

```dax
Заёмщиков с остатком =
VAR _anchor = LASTNONBLANK ( dim_month[Date], [_Остаток (сумма)] )
RETURN
    SWITCH (
        TRUE (),
        HASONEVALUE ( dim_product[product_key] ),
            CALCULATE ( SUM ( fact_stock[borrowers_with_balance] ), _anchor ),
        HASONEVALUE ( dim_source[l_source] ) && NOT ISFILTERED ( dim_product ),
            CALCULATE ( SUM ( fact_borrowers[borrowers_with_balance] ), _anchor )
    )

Остаток на заёмщика = DIVIDE ( [Общий остаток], [Заёмщиков с остатком] )
```

### Сравнение м/м и г/г — одной группой вычислений на все меры

```dax
-- группа вычислений «Сравнение»
Значение  = SELECTEDMEASURE ()

Изм. м/м =
VAR _idx = SELECTEDVALUE ( dim_month[month_idx] )
VAR _prv = CALCULATE ( SELECTEDMEASURE (), REMOVEFILTERS ( dim_month ), dim_month[month_idx] = _idx - 1 )
RETURN DIVIDE ( SELECTEDMEASURE () - _prv, _prv )

Изм. г/г =
VAR _idx = SELECTEDVALUE ( dim_month[month_idx] )
VAR _prv = CALCULATE ( SELECTEDMEASURE (), REMOVEFILTERS ( dim_month ), dim_month[month_idx] = _idx - 12 )
RETURN DIVIDE ( SELECTEDMEASURE () - _prv, _prv )
```

Для долей (уровень просрочки, покрытие, доля досрочных) относительное изменение
доли вводит в заблуждение — рост с 2 % до 3 % читается как «+50 %». Для них
показывать уровень, а изменение — в процентных пунктах, отдельной мерой.

## Раскладка как в прежнем Excel

**Исправлено 24.09.2026.** Прежняя редакция предлагала параметр полей в строках

**Параметр полей в строках матрицы.** Моделирование → Новый параметр → Поля →
отметить меры. Получается таблица-«показатель», которая ведёт себя как измерение:

- **Виток 0.** Матрица: строки — `Показатель`, столбцы — `dim_month[Месяц]`,
  фильтр — `Последние 12 = TRUE`. Итоги без разложения.
- **Виток 1.** Та же матрица, в строки вторым уровнем — `dim_source[Источник]`.
  Получается блок на показатель, внутри — источники, в столбцах — 12 месяцев.
  Ровно прежняя раскладка Excel.

Дальше каждый виток добавляет в строки следующий уровень той же матрицы.

## Конфиденциальность

**В модели только агрегаты `месяц × источник`.** Договоров, заёмщиков и ИИН
в ней нет — всё это остаётся внутри SQL. Поэтому файл Power BI можно показывать
внутри Банка, не опасаясь за ПДн.

**`.pbix` в репозиторий не коммитится.** В режиме импорта он хранит данные внутри
себя, а §2 корневого `CLAUDE.md` запрещает собранные данные в репозитории. В
репозитории — только текст: SQL, DAX и этот файл. Когда модель устоится, её
определение можно хранить в формате проекта Power BI (`.pbip`, TMDL — текстовые
файлы, которые диффятся), исключив кэш данных из коммита.

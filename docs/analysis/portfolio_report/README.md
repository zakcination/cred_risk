# Контур `portfolio_report` — сегментный отчёт по кредитному портфелю

Заведён 23.09.2026. Ежемесячный управленческий отчёт по портфелю в разрезе **сегментации**,
а не продуктов. Единственный источник — **`Dictionaries.risk_analytics`**.
**Исключение с 28.09.2026 — стадии** (решение автора): Stage 3 + 4 берётся из `CL_PORTFOLIO` —
`category` у S03 и S02, `Basket` у S17 и S01. Только стадия; деньги и продукт — из витрины.

## Почему витрина, а не `CL_PORTFOLIO`

`AQR20xx_B1A/B1B/B3C_*` — замороженные регуляторные выгрузки циклов, **не месячные**.
Это записано в `sql/stage3_safezone_discovery.sql` как прямое предупреждение. Для
повторяющегося отчёта они непригодны по построению: снимок цикла — не поток.

## Архитектура: четыре слоя

Схема взята из отраслевого образца (корейский отчёт по автопортфелю) и проверена
на применимость к нашим данным.

| Слой | Что отвечает | Состояние |
|---|---|---|
| **Поток** | что вошло в портфель и что вышло | **строится** — `l_funding_date` заполнена на 100 % по всем четырём источникам |
| **Запас** | что лежит сейчас | строится — `loan_account` с фильтром по статусу |
| **Риск** | что портится | строится на **остатке счёта 1424**, не на полях дней — см. отзыв ниже |
| **Разрезы** | где именно портится | частично, см. ограничения |

Ключевое открытие: **поток строится не сравнением снимков, а по датам внутри одного.**
`loans` историзована на одну дату (01.09.2026), но несёт `l_funding_date`,
`l_first_repayment_date` и `l_actual_closure_date` — вход и выход читаются без истории.

## Два отозванных вывода

**Отзыв 1 — провизии в витрине есть.** Прежняя формулировка: «провизии по займам —
нет; есть только по гарантиям и условным обязательствам». Неверно. Они лежат не под
именем, а **счетами**, и формула зарегистрирована в `risk_analytics_data_model.md`:

```
provisions_total = la_account_1428 + la_account_1845 + la_account_18771
```

Поиск по маскам `%provis%`, `%reserv%`, `%ecl%` их не находил. Нашлись только когда
вывели список колонок целиком. Метрика «покрытие провизиями» **разблокирована**:
на 01.09.2026 по счетам в статусе «Открыт» — 113,3 млрд ₸.

**Отзыв 2 — `delinquency_bucket` не является лестницей просрочки.** Прежняя
формулировка: «просрочку считать по `delinquency_bucket` (97,9 % заполнения)».
Заполненность высокая, но смысл не установлен, и данные его опровергают:

| Источник | корзина 1 | корзина 2 | корзина 3 |
|---|---|---|---|
| S01 | 0 … 27 | 0 … 90 | **0** … 6041 |
| S03 | 3 … **950** | 3 … 91 | **1** … 5465 |
| S17 | 6 … 29 | 6 … 90 | **6** … 1778 |
| S02 | `days_past_due` 100 % NULL — проверить нечем |

Диапазоны перекрываются на каждом источнике. Структура корзин тоже различается:
у S01 и S03 есть корзина 4, у S02 и S17 — `NULL`.

**Чем мерить вместо этого: остатком счёта 1424.** По S17 соответствие точное —
`la_account_1424 <> 0` даёт 11 518 счетов, и ровно на этих же 11 518
заполнен `days_past_due_principal`. Признак работает одинаково на всех четырёх
источниках: **37 019** счетов из 345 853 — 10,7 %.

## Отбор действующего договора

Источник правила — `dict_registry/status_map.csv`.

```sql
      (   (l.l_source = 'S01' AND l.l_loan_status = N'О')      /* CP1251 206 */
       OR (l.l_source = 'S02' AND l.l_loan_status = 'Account OK')
       OR (l.l_source = 'S03' AND l.l_loan_status = 'O')       /* латиница 79 */
       OR (l.l_source = 'S17' AND l.l_loan_status = N'О') )    /* CP1251 206 */
  AND l.l_actual_closure_date IS NULL
```

Два условия вместе, а не порознь. Даёт **541 416** договоров из 8 231 917 (6,6 %).

**Правило заведомо занижает портфель** на договоры неопределённого статуса: **4 756**
(редакция 23.09.2026 — «примерно 32 900»; из `status_map.csv` не воспроизводилось,
было 28 542, из них 23 786 — S17 `Т`, переведённый в «закрыт» прогоном DICT_D). Недобор виден при сверке с расчётом провизий, перебор — нет.

**Гомоглифы.** Латинская `O` (код 79) у S03 и кириллическая `О` (206) у S01 и S17
на экране неразличимы. Условие по источнику обязательно; общее `IN ('O', N'О')` —
источник ошибки, которая ничем себя не выдаёт.

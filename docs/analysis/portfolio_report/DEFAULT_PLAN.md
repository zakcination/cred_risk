## Сильнейший контраргумент — первым

**В витрине нет ни стадии, ни надёжной глубины просрочки** (README, «Ограничения»).
Любой «дефолт», построенный на витрине, — **конструкция по правилу**, а не
классификация Банка. Она разойдётся с отчётностью по провизиям, и вопрос «почему
у вас Stage 3 не такой, как у расчёта провизий» будет задан первым. Поэтому:

1. Метрики этого плана называются **«дефолт по правилу ДФ-1»**, а не «Stage 3»,
   пока источник — конструкция на витрине. Stage 3 + 4 — только из поля, которое
   стадию хранит: `delinquency_bucket`, если устоит Р-9, либо система провизий
   (развилка ДФ-5).
2. Сверка с официальной стадией на общей дате — обязательный контроль, а не
   украшение (§5 «Контроли»). Без неё правило не принимается.

Второй контраргумент — к поколениям: история `loan_account` — 21 срез
(01.2025 … 09.2026). Дефолт по сроку «90+» вызревает к возрасту 4–6 месяцев,
поэтому у когорт после ~04.2026 кривая дефолта будет почти пустой. Это свойство
окна, а не качества поздних когорт.

## 1. Структурный подход

Три метрики — один признак. Сначала определяется **состояние «в дефолте» на срезе**,
из него выводятся все три:

| Метрика | Что это | Из состояния |
|---|---|---|
| **Новые дефолты** (поток) | договоры, **вошедшие** в дефолт за месяц: количество и объём | переход «не в дефолте на срезе `t−1`» → «в дефолте на срезе `t`» |
| **Stage 3 + 4 / запас в дефолте** (запас) | договоры в дефолте на конец месяца: количество и остаток, доля от портфеля | состояние на срезе `t` |
| **Уровень дефолта по поколениям** | доля договоров когорты выдач, **хотя бы раз** вошедших в дефолт к возрасту `k` | накопленное состояние по возрастам |

**Единица наблюдения** — договор (развилка ДФ-2). **Месяц события** — по соглашению
отчёта: срез 1-го числа `t` описывает конец месяца `t−1` (как у запаса в `fact_stock`).

**Цензурирование.** Первый срез 01.01.2025 не даёт «нового» дефолта — не с чем
сравнить; ряд новых дефолтов начинается с 01.2025 (срез 01.02.2025). Договор,
уже бывший в дефолте на первом срезе, «новым» не считается никогда в окне — это
левое цензурирование, и оно занижает первые месяцы при ДФ-3 «повторный = новый».

## 3. План сбора

| Что | Откуда | Период |
|---|---|---|
| состояние на срезе: дни, остаток, 1424 | `loan_account`, открытые счета (`la_status = N'Открыт'`) | срезы 01.2025 … 09.2026 |
| продукт, когорта, сумма выдачи | `loans` — `product_key` как в `PBI_fact_flow.sql` | когорты 12.2024 … |
| списание S03 | `loans`, статус `I`, `l_actual_closure_date` | 24 мес |
| реструктуризация | `restructuring_v2` — если войдёт в ДФ-1 | срезы окна |
| стадия банка | **вне витрины** — только при ДФ-5 (а) | общие даты |

**Связь** — `la_gid = l_gid AND la_source = l_source`, как в фактах Power BI.
**Дубли** — счёт на срезе один; если DEF_0 покажет иначе — агрегат по `la_gid`.
**Пропуск среза у счёта** — состояние не выдумывается: пропущенный срез — «не наблюдён»,
а не «не в дефолте».

## 4. План обработки

**Факты для Power BI** — по образцу существующих, один оператор без `GO`:

| Факт | Зерно | Колонки |
|---|---|---|
| `fact_default` | месяц × источник × продукт | `new_def_cnt`, `new_def_balance`, `in_def_cnt`, `in_def_balance`, `cured_cnt` |
| `fact_vintage` | когорта × продукт × возраст | `cohort_cnt`, `cohort_amount`, `ever_def_cnt`, `ever_def_amount`, `observed` — рядом с `ever_overdue_*` из `VINTAGE_PLAN.md` |

**Формулы:**

- доля в дефолте = `in_def_balance` / остаток портфеля того же среза (и по количеству);
- уровень новых дефолтов за месяц = `new_def_cnt` / договоры **не** в дефолте на `t−1`;
- годовой уровень дефолтов (опционально, для сравнения с PD) — по EBA/GL/2017/16:
  вошедшие за 12 месяцев / не бывшие в дефолте на начало 12 месяцев;
- поколения: `ever_def_cnt(k)` / `cohort_cnt` и то же в сумме выдачи; точки дальше
  наблюдаемого возраста не строятся.

## Результат DEF_0 — 28.09.2026

Разведка, не метрики. Критерии записаны до прогона — ниже по ним, без подгонки;
где критерий оказался плохо поставлен, это сказано отдельно.

**Имена.** Все 16 на месте; поля дней и корзина — `int`, флаг реструктуризации —
`nvarchar`. Поиск по маскам нашёл то, чего план не знал: в `loan_account` ещё шесть полей
дней (`days_past_due_overdue_principal`, `…_interest`, `…_overdue_interest_principal`,
`…_account_1879`, `…_1838`, `…_1860`), в `credit_lines` — `cl_basket_report_date`.
Поля с именем стадии нет.

**Предложенный порог не выполнен ни на одном источнике** (≥ 90 % пар «прирост = дни»).
Но порог поставлен плохо, и это моя ошибка: шапка DEF_0 сама относит «прирост меньше дней»

месте. Признак дефекта — прирост **быстрее** календаря; его 0,08–1,8 %. Замена критерия
после прогона — post hoc, поэтому решение за автором: по записанному порогу поле
отвергнуто; по доле «быстрее дней» — принято для S01, S03, S17.

| прочие | **по предложениям**: договор; объём — остаток на срезе входа; поколения — **S01 + S03 + S17** (так сформулирован вопрос; В-4 предлагал S03 + S17), исход накопленный, два веса, месяц с укрупнением < 300 в квартал | `powerbi/PBI_fact_default.sql`, `powerbi/PBI_fact_vintage.sql` |

**Сильнейший довод против ДФ-5 — записан, решение не меняет.** По `FINDINGS.md` корзина
витрины совпадает с `Basket` старой ветки на 99,93 % (S01) и 99,98 % (S17). Если это держится,
стадия из CL_PORTFOLIO и «не стадия» из витрины — одно и то же число. `STG_0` блоки 4–5
измеряют это на трёх срезах; при совпадении вопрос 10 README решается данными.

**Что следовало из первого круга и требовало решения** (закрыто вторым кругом):

- **Stage 3 + 4 — источника нет.** Стадий в витрине нет, корзина — не стадия. Помесячный
  ряд строится только как **запас в дефолте по правилу** с подписью «не стадия», либо
  из системы провизий — это открытый вопрос 5 README.
- **Смена смысла поля дней в 07.2026** (S01, S17: с этого среза дни стоят ровно там, где
  `la_account_1424 <> 0`; раньше — ещё ~700 счетов S01 без 1424, из них 280 с 90+).
  Без поправки ряд 90+ по S01 даст искусственный обрыв: 90+ — 1 016–1 022 счёта на срезах
  2025 года против 293 на 09.2026, а заполненных дней — 955 → 400 ровно в 07.2026.
  Предложение — считать 90+ **при `la_account_1424 <> 0`**: весь ряд на нынешнем смысле
  поля. Цена — не видна просрочка только по вознаграждению.
- **Граница «более 90».** Методика: дефолт с 91-го дня. Модель данных отмечает, что отчёт
  показывает `days_past_due − 1` — витрина считает и день среза. Для поля по основному долгу
  такой пометки нет; правило берёт поле как есть: `> 90`. Сдвиг на день касается единиц
  счетов на границе.

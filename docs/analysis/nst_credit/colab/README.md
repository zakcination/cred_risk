# Сегментация: правила эталона и разбор прежних правил банка

`segment_rules_colab.ipynb` — для Google Colab, `segment_rules_colab.py` — тот же
код ячейками `# %%` для локального запуска. Файлы синхронны: `.ipynb` собирается
из `.py`.

## Постановка

В рабочей таблице B1A две колонки сегментации:

| Колонка | Что это |
|---|---|
| `segment_afr` | **эталон** — сегментация АФР |
| `segment_eub` | как банк делил **раньше** |

Скрипт решает три задачи: восстанавливает правила эталона, собирает из них
готовый SQL `CASE`, и разбирает, **где прежние правила ошибались и на каком
объёме**.

Правится одна ячейка — `CONFIG`: путь к файлу, имена двух колонок сегментации,
собственный капитал и отчётная дата.

## Что получается на выходе

| Файл | Содержание |
|---|---|
| `pravila_segmentacii.txt` | правила по каждому сегменту «ЕСЛИ … ТО …», значимые колонки, полное дерево |
| `segmentation_case.sql` | **готовый SQL CASE**, восстановленный из эталона |
| `perehody.csv` | переходы «было ЕАБ → стало АФР» с объёмами |
| `znachimye_kolonki.csv` | колонки, ранжированные по вкладу в решение |
| `spravochnik_znacheniy.csv` | по каждой значимой колонке — значения, частоты, в какие сегменты ведут |

## Разбор расхождений — три среза

1. **Матрица переходов**: сколько договоров и куда переехало.
2. **Дерево на признаке расхождения**: что отличает строки, где прежние правила
   разошлись с эталоном. Это прямой ответ на вопрос «в чём именно был неправ
   старый скрипт».
3. **Разбор каждого крупного перехода**: внутри строк, которым банк присвоил `A`,
   ищется, что отличает те, которые эталон относит к `B`.

## Проверка на синтетике

Сгенерирована выгрузка той же структуры (40 000 строк, 11 сегментов) с эталоном
по известным правилам и «прежней» сегментацией, в которую внесены **три
намеренных дефекта**:

| Дефект | Строк | Что нашёл скрипт |
|---|---|---|
| `RETEST` ставился по метке продукта без проверки залога | 81 | `portfolio == 'Mortgage'` И `collateral == '0'`, чистота 100 % |
| порог индивидуальных применялся к договору, а не к заёмщику | 251 | `eng_share_capital > 0.00200061`, чистота 100 % |
| ИП уходили в розницу вместо малого бизнеса | 1 131 | `debtor_se == '1'` И `debtor_type != '1'`, чистота 100 % |

Все три восстановлены, включая точный порог 0,2 %. Разбор переходов независимо
показал то же самое: `RETCON → RETSML` объясняется признаком ИП,
`RETCON → Individual loans` — порогом от капитала, `RETEST → RETCON` — залогом.

Точность модели на эталоне 0,9981, macro-F1 0,97.

## Оговорки

**Проверка на тавтологию — читать первой.** Если `segment_afr` окажется выходом
нашего же скрипта, а не независимым ответом АФР, дерево просто выучит наш `CASE`
и покажет почти идеальное качество на тех же колонках. Это не подтверждение
правил. Скрипт проверяет это явно: печатает точность и список колонок **вне**
веток действующего скрипта. Точность ≈ 1,0 при пустом списке — сигнал уточнить
источник эталона, а не радоваться результату.

**Порядок веток в сгенерированном SQL — наше решение, а не эталон.** Таблица 4
Методруководства задаёт лишь частичный порядок (`GROUND_TRUTH_SEGMENTS.md`,
раздел 3), а `CASE` требует полного. Ветки упорядочены списком `PRIORITY`
в конфигурации; внутри сегмента — по чистоте.

**Сгенерированный SQL нельзя применять без сверки.** Дерево находит корреляцию.
Правило вида «`loan_purp <> '7'`» может оказаться артефактом выборки, а не нормой.
Каждая ветка сверяется с `GROUND_TRUTH_SEGMENTS.md` перед тем, как попасть
в рабочий скрипт.

**Из признаков исключены `stage`, `ead_n`, `amount`** — это производные колонки
того же скрипта сегментации, они дали бы утечку.

**ПДн.** `iin_bin` нужен для агрегата по заёмщику и удаляется сразу после его
расчёта, `name`, `contract_number`, `account_no` — на том же шаге. Но исходный
файл загружается целиком, поэтому Colab — внешний сервис — для боевых данных
не годится: тот же `.py` запускается локально без единой правки.

**Сегменты меньше 30 строк** пропускаются: правило по ним неотличимо от подгонки.

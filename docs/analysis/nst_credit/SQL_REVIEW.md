# Разбор действующих скриптов сегментации и расчёта метрик

Два скрипта: сегментация (`segment_afr` для B1A и B1B) и расчёт средневзвешенных
риск-метрик по (сегмент × стадия). Замечания упорядочены по влиянию на результат.
Обновлено 20.08.2026.

---

## Критично: искажает значения метрик

### 1. Обнуление заглушек занижает средневзвешенные

```sql
CASE WHEN gg.lgd IN ('1111111111111','9999999999999') THEN 0 ELSE CAST(gg.lgd AS FLOAT) END AS lgd_new
...
ISNULL(d.lgd_new * d.ead / NULLIF(a.ead_total, 0), 0) AS lgd_sred
```

Заглушка означает «значение отсутствует», а не «значение равно нулю». Сейчас такой
заём входит в знаменатель `ead_total` со своим EAD, но добавляет в числитель ноль —
средневзвешенная метрика по сегменту занижается пропорционально доле заглушек.

**Предложение.** Исключать заглушки из обеих частей: считать веса только по займам
с известной метрикой.

```sql
-- вес и вклад считаются на одном и том же множестве
SUM(CASE WHEN lgd_new IS NOT NULL THEN ead END) OVER (PARTITION BY segment_afr, stage_b_new) AS ead_lgd_base
```

И обязательно выводить долю заглушек по каждому (сегмент × стадия) — это одновременно
метрика заполняемости, за которую отвечает БРМ.

### 2. Отсутствует средневзвешенная по `pd_ol`

`pd_ol_new` вычисляется, но `pd_ol_sred` не считается — в отличие от `pd_c12_sred`
и `pd_cl_sred`. Либо поле не нужно (тогда убрать из расчёта), либо нужно (тогда
добавить), но асимметрия не должна оставаться незамеченной.

### 3. Несопоставленные сегменты исчезают молча

```sql
LEFT JOIN [personal_tables].[dbo].[RA_NST_segment_AQR2025] fg ON gg.loan_id_kr = fg.loan_id_kr
```

При отсутствии соответствия `segment_afr` равен `NULL`, и такие займы попадают
в группу `NULL` при агрегации — без предупреждения. В фактической выгрузке
сегментации кода `X` нет вовсе, что подозрительно (см. `SEGMENTS.md`, находка 3).

**Предложение.** Контрольный запрос перед расчётом:

```sql
SELECT COUNT(*) AS rows_total,
       SUM(CASE WHEN segment_afr IS NULL THEN 1 ELSE 0 END) AS no_segment,
       SUM(CASE WHEN segment_afr = 'X'  THEN 1 ELSE 0 END) AS segment_x
FROM ...;
```

Расчёт не запускается, пока `no_segment + segment_x` не объяснены.

## Существенно: влияет на состав сегментов

### 4. Порядок ветвления: `ENT_TYPE` проверяется раньше признаков розницы

Шаги 7 и 8–10 в `CASE`: `ENT_TYPE in (1,2,3)` срабатывает **до** проверки
`DEBTOR_TYPE = 0` (физическое лицо). Если у розничного займа заполнен `ENT_TYPE`
(что не исключено при выгрузке из разных систем), он уйдёт в `CORLAR`, `CORMED`
или `RETSML` вместо `RETEST`/`RETCAR`/`RETCON`.

**Проверка на данных** (одна строка, до расчёта):

```sql
SELECT ent_type, COUNT(*) FROM ... WHERE debtor_type = 0 AND ent_type IN (1,2,3) GROUP BY ent_type;
```

Если результат не пуст — порядок ветвления нужно менять: сначала отделять ФЛ.

### 5. Индивидуальные займы и ОУСА не перераспределяются

По Таблице 3 Методруководства эти два портфеля для кредитного риска
«распределены по другим портфелям». В скрипте они остаются самостоятельными
значениями `segment_afr`. Нужен отдельный шаг: сохранять **продуктовый** сегмент
займа рядом с признаком «индивидуальный / ОУСА», чтобы для кредитного риска
считать по продуктовому, а для ЧПД — по портфелю AQR.

**Предложение.** Две колонки вместо одной: `segment_aqr` (как сейчас)
и `segment_nst_credit` (продуктовый, без DISASS и Individual loans).

### 6. Порог индивидуальной значимости зашит числом

```sql
>= 461235157000 * 0.002   -- капитал на 01.01.2025
```

При смене отчётной даты порог молча остаётся прошлогодним.

**Предложение.** Вынести в параметр (переменная, таблица параметров или CTE
с одной строкой) и указывать дату капитала рядом со значением.

### 7. `RETEST` определяется по `portfolio = 'Mortgage'`, признак залога отключён

```sql
--    and coalesce(cast(collateral as float), 0) = 1
    and portfolio in ('Mortgage') then 'RETEST'
```

Портфель НСТ называется «Займы физических лиц, обеспеченные жилой недвижимостью»,
то есть определяющим является обеспечение, а не метка продукта. Сейчас классификация
опирается на `portfolio`, а проверка залога закомментирована. Нужно решение: либо
вернуть условие, либо обосновать, что метка `Mortgage` эквивалентна обеспечению жильём.

### 8. `RETCAR` = «обеспеченные», но без различения вида обеспечения

Шаг 9 относит к `RETCAR` любой обеспеченный заём ФЛ (`collateral = 1`), тогда как
портфель называется «Автокредиты и прочие обеспеченные займы». Формально совпадает
с названием, но стоит зафиксировать в пояснительной записке, что автокредиты
и прочие обеспеченные не разделяются.

## Методологически: требует фиксации

### 9. База задолженности в B1A и B1B считается по-разному

- B1A: `od + od_del + interest + interest_del + correction + disc_prem + penalty`
- B1B: `correction + disc_prem + penalty`

Для кредитных линий (B1B) отсутствие основного долга объяснимо, но это должно быть
описано явно — иначе при сверке сумм расхождение выглядит как ошибка. Кроме того,
включение `penalty` не следует из определения задолженности в п. 44 Методруководства
(см. `GLOSSARY.md`, открытый вопрос 1).

### 10. Приведение стадий фиксируется как допущение

`stage_b = 4 → 3` и `stage_b = '1111111111111' → 1`. Второе особенно чувствительно:
заглушка трактуется как отсутствие обесценения. Нужно посчитать, сколько таких
записей и на какую сумму, и указать это в пояснительной записке.

```sql
SELECT stage_b, COUNT(*) n, SUM(CAST(ead AS FLOAT))/1e9 ead_mlrd
FROM ... GROUP BY stage_b ORDER BY n DESC;
```

### 11. Агрегат считается по факту, а не по периметру НСТ

`AGG` группирует всё, что прошло фильтр `is_del = '0'`. Портфели, которые
по Таблице 3 в кредитном риске **не анализируются** (займы финансовым институтам,
государственным структурам, дебиторская задолженность), должны исключаться
из расчёта метрик кредитного риска — иначе средневзвешенные считаются по более
широкому множеству, чем требуется.

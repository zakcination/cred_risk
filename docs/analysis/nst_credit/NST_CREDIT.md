```
если loan_obj = 1        → RETEST
иначе если collateral = 1 → RETCAR
иначе                     → RETCON
```

Проверка: `RETEST` 45 + 748 = 793 (у АФР 794); `RETCAR` 103 327 + 61 + 12

`loan_obj` определяет `RETEST`, `collateral` определяет `RETCAR` против
`RETCON`. Наше правило берёт `portfolio IN ('Mortgage')` — оно и даёт
48 ошибок в `RETEST`. Замена на `loan_obj = 1` закрывает розницу полностью.
**Р2 решена.**

берёт `loan_obj IN (1,2,3)` и код `11` пропускает — отсюда часть недобора

**Совпадение действующего скрипта с `segment_afr` — 99,99 %:**
95 расхождений на 731 159 договоров.

**Вывод о природе таблицы.** `RA_NST_segment_AQR2025.segment_afr` — это
**первичная сегментация AQR**, которую наш скрипт воспроизводит, а не
независимый эталон АФР для контура кредитного риска. Это согласуется с п. 29
дословно: «первичная сегментация выполняется **в рамках AQR**».

Практическое следствие, важнее самого факта: **`segment_afr` не может
рассудить два варианта правил.** При совпадении 99,99 % он подтвердит любой
вариант, близкий к действующему скрипту, и отвергнет любой другой — независимо
от того, какой из них соответствует Таблице 4. Калибровать по нему правила
нельзя; им можно только контролировать, что скрипт не сломан.

### 3.0а. Что из этого следует для двухслойной модели

Картина, которая сходится и с документом, и с данными:

| Слой | Что делает | Где мы |
|---|---|---|
| **1. Первичная сегментация AQR** | даёт 16 портфелей, включая `Individual loans`, `DISASS`, `RELATE` как самостоятельные | **сделано, 99,99 %** — скрипт воспроизводит |
| **2. Перераспределение по Таблице 3** | `Individual loans`, `DISASS`, господдержка раскладываются по продуктовым портфелям | **не построено** |

Слой 1 менять не нужно — он верен. Слой 2 — отдельный шаг **поверх**,
а не замена слоя 1. Именно так надо было формулировать Р1 (см. 6а).

### 3.2. Розницу определяют `loan_obj` **и** `collateral` вместе

Разрез `loan_obj × collateral × segment_afr`, розница (`debtor_type = 0`,
`debtor_se = 0`):

|---|---|---|---|
| 1 жильё | 0 | `RETEST` | 44 |
| 1 жильё | 1 | `RETEST` | 741 |
| **6 авто** | **0** | **`RETCON`** | **1 830** |
| **6 авто** | **1** | **`RETCAR`** | **103 237** |
| 8 потреб. | 0 | `RETCON` | 620 536 |
| 8 потреб. | 1 | `RETEST` | 36 |
| 8 потреб. | 1 | `RETCAR` | 24 |

**Ключевая строка — `loan_obj = 6`.** При `collateral = 0` заём идёт
в `RETCON`, при `collateral = 1` — в `RETCAR`. Один и тот же объект

Это опровергает правило «розница делится только по `loan_obj`»
(`_archive/TREE_RUN_2.md`, раздел 4), где `loan_obj = 6 → RETCAR` заявлено
с чистотой 100 % на 103 341 строке. Фактически 1 830 договоров с тем же
`loan_obj = 6` идут в `RETCON`. Дерево их не увидело, потому что они
составляют 1,7 % ветки и попали в допуск чистоты.

`loan_obj = 1` — единственный, где залог не влияет: `RETEST` в обоих случаях.

### 3.3. `ent_type` ошибочным не является — отзыв

**Отзывается утверждение**, что `ent_type` согласуется с эталоном на 57–72 %
и что «каждый третий-четвёртый корпоративный договор эталон относит не туда»
(`_archive/TREE_RUN_2.md`, раздел 5). На нём было построено решение Р3
и запрос О2.

Фактический разрез (таблица в 3.0) объясняется **порядком каскада**, а не
качеством поля. Ветка `Individual loans` стоит **выше** веток `ent_type`,
поэтому крупные заёмщики перехватываются ею раньше: 87 % `ent_type = 1`,
39 % `ent_type = 2`, 23 % `ent_type = 3` уходят в `Individual loans`.

Если убрать перехват, соответствие такое:

| `ent_type` | Ушло в `Individual loans` | Из остатка — «свой» сегмент |
|---|---|---|
| `1` крупный | 456 | `CORLAR` 56 из 68 = **82 %** |
| `2` средний | 315 | `CORMED` 484 из 493 = **98 %** |
| `3` малый | 718 | `RETSML` 2 312 из 2 369 = **98 %** |

Дрейфа «малый → средний → крупный», о котором говорил разбор дерева,
в данных **нет**. Остаток вне «своего» сегмента у среднего и малого — 2 %,
и это `RELATE`, `COREST`, `DISASS`, то есть ветки с более высоким приоритетом,
а не ошибка размера.

**Следствие: О2 снимается, Р3 переформулируется.** Снимок РСП не нужен —
поле работает. Ошибка была в методе измерения, а не в данных.

Остаётся честная оговорка: проверить `ent_type` **против статьи 24** по-прежнему
нечем, численности работников и годового дохода в выгрузке нет. Но
«не проверено внешним источником» и «расходится на четверть» — разные
утверждения, и второе было неверным.

### 3.3а. ИП с розничным займом — вторая ось ошибки

Замечание Sabila: ИП берёт потребительский заём. Куда он должен попасть?

`ent_type` и `debtor_se` — атрибуты **заёмщика**, `loan_obj` — атрибут **займа**.
ИП одновременно физическое лицо и субъект малого предпринимательства
(ст. 24 п. 3 прямо: «индивидуальные предприниматели без образования
юридического лица»). Наши правила выбирают сегмент по статусу заёмщика,
а не по назначению займа.

Механика: розничная ветка каскада требует `debtor_se = 0`. ИП её не проходит
никогда и проваливается в `ent_type = 3 → RETSML` — независимо от того,
оборотка это или потребительский заём.

**Масштаб не установлен.** Цифра «1 206 договоров, больше половины `RETSML`»
взята из `_archive/TREE_RUN_2.md`, а этот источник по трём другим пунктам
уже опровергнут прогоном (см. 3.0–3.3). Пользоваться ею нельзя.
Д4 на момент 24.08.2026 **не прогонялся** — вопрос открыт и по сути,
и по масштабу.

Что известно точно из прогона Д3: в `ent_type = 3` (малый) — 3 087 договоров,
из них 2 312 в `RETSML`, 718 в `Individual loans`. Сколько среди них ИП
и как эталон делит их по назначению займа — покажет Д4.

В разрезе по `ent_type` (п. 3.3) этот эффект **не виден**: там дрейф по размеру
(малый → `CORMED` 21 %, `CORLAR` 4 % — вверх), а эффект ИП толкает в розницу.
Это отдельный тип ошибки — **тип G**.

**Контраргумент против правки.** Таблица 4 определяет `RETSML` по субъекту
(«Займы субъектам малого предпринимательства») и **без оговорки о назначении**,
тогда как у `CORLAR` и `CORMED` оговорка «кроме инвестиционных и выданных
на приобретение, строительство недвижимости» стоит явно. Асимметрия намеренная.
При буквальном чтении любой заём ИП, включая потребительский, принадлежит
`RETSML`, и текущее поведение верно.

**Разрешается эталоном, а не текстом** — запрос Д4. Гипотеза **Г5**.

## 6а. Принятые решения

> Редакция после Д7. Р1 прошла путь «принято → отозвано → восстановлено»:
> отзыв опирался на сверку с подачей банка, а не с эталоном. Записано так,

сегмента.** У АФР их нет вовсе (3я.1). Заём классифицируется по продукту,
признаки идут отдельными колонками — они нужны для ЧПД, где Таблица 3

**Р3 — ВОЗВРАЩЕНА В ИСХОДНОЙ РЕДАКЦИИ. `ent_type` расходится с эталоном.**

### Д7. Присоединить сегмент АФР к нашей выгрузке как `afr_segment_approved`

Цель: рядом с нашим `segment_afr` встаёт утверждённый АФР сегмент, и расхождение
видно построчно.

**Шаг 1. Предполётная проверка — без неё соединять нельзя.**

В таблице АФР четыре кандидата на ключ. Если по `LOAN_ID_KR` есть дубли,
`LEFT JOIN` размножит строки нашей выгрузки, и любые доли после этого будут
неверны — причём тихо, без ошибки.

```sql
SELECT 'АФР: ключей с дублями' AS check_name, COUNT(*) AS cnt
FROM (SELECT LOAN_ID_KR
      FROM [CL_PORTFOLIO].[dbo].[RA_NST_segment_AQR2025_ot_AFR]
      WHERE LOAN_ID_KR IS NOT NULL
      GROUP BY LOAN_ID_KR HAVING COUNT(*) > 1) t
UNION ALL
SELECT 'АФР: дубли с РАЗНЫМ сегментом', COUNT(*)
FROM (SELECT LOAN_ID_KR
      FROM [CL_PORTFOLIO].[dbo].[RA_NST_segment_AQR2025_ot_AFR]
      WHERE LOAN_ID_KR IS NOT NULL
      GROUP BY LOAN_ID_KR HAVING COUNT(DISTINCT SEGMENT) > 1) t
UNION ALL
SELECT 'АФР: LOAN_ID_KR пуст', COUNT(*)
FROM [CL_PORTFOLIO].[dbo].[RA_NST_segment_AQR2025_ot_AFR]
WHERE LOAN_ID_KR IS NULL
UNION ALL
SELECT 'наша выгрузка: ключей с дублями', COUNT(*)
FROM (SELECT loan_id_kr
      FROM [personal_tables].[dbo].[RA_NST_segment_AQR2025]
      GROUP BY loan_id_kr HAVING COUNT(*) > 1) t;
```

**Результат прогона 24.08.2026 — ключ чистый:**

| Проверка | Значение |
|---|---|
| АФР: ключей с дублями | **0** |
| АФР: дубли с разным сегментом | **0** |
| АФР: `LOAN_ID_KR` пуст | **0** |
| наша выгрузка: ключей с дублями | **0** |

`LOAN_ID_KR` — уникальный ключ с обеих сторон. Соединение 1:1, размножения
строк не будет, схлопывание через `GROUP BY` не нужно, `COALESCE`
с `CREDIT_LINE_ID` не нужен. Шаги 2–4 идут в прямой редакции.

**Шаг 3. Перечень правок АФР. Это главный результат контура.**

Каждая ячейка вне диагонали — дефект, который регулятор поймал и исправил

```sql

      p.segment_afr   AS bank_do_proverki
    , a.SEGMENT       AS afr_utverdil
    , COUNT(*)        AS contracts

ORDER BY CASE WHEN p.segment_afr = a.SEGMENT THEN 1 ELSE 0 END, contracts DESC
OPTION (MAXDOP 1);

с `afr_utverdil = NULL` — договоры, которых у АФР нет вовсе; их разбирать
отдельно, это вопрос периметра, а не правил.

тавтология того же рода, что три дня сверки с подачей банка. Выгрузка
для дерева этот риск описывала прямо: метрики AQR калиброваны по сегменту,
и модель выучит «`lgd` = 0,695 → `CORLAR`» вместо настоящего правила.

`kateg_vzveshivania` менее уязвим: категория взвешивания по № 170 —
классификация контрагента, а не производная от сегментации AQR. С него
и начинать.

### В1. Валидация новых правил на 2024 Q4 — решающий прогон

SET NOCOUNT ON;
DECLARE @capital float = 461235157000;   -- СК на 01.01.2025
DECLARE @thr_ind float = 0.002;

IF OBJECT_ID('tempdb..#nst_v1') IS NOT NULL DROP TABLE #nst_v1;

    SELECT
          b.loan_id_kr, b.iin_bin, b.entity, b.lsboo, b.portfolio
        , TRY_CAST(b.f_inv       AS int) AS f_inv_n
        , TRY_CAST(b.debtor_type AS int) AS debtor_type_n
        , TRY_CAST(b.debtor_se   AS int) AS debtor_se_n
        , TRY_CAST(b.ent_type    AS int) AS ent_type_n
        , TRY_CAST(b.loan_obj    AS int) AS loan_obj_n
        , TRY_CAST(b.loan_purp   AS int) AS loan_purp_n
        , TRY_CAST(b.collateral  AS int) AS collateral_n
        , COALESCE(TRY_CAST(b.ead AS float), 0) AS ead_n
        , COALESCE(TRY_CAST(b.od           AS float), 0)
        + COALESCE(TRY_CAST(b.od_del       AS float), 0)
        + COALESCE(TRY_CAST(b.interest     AS float), 0)
        + COALESCE(TRY_CAST(b.interest_del AS float), 0)
        + COALESCE(TRY_CAST(b.correction   AS float), 0)
        + COALESCE(TRY_CAST(b.disc_prem    AS float), 0)
        + COALESCE(TRY_CAST(b.penalty      AS float), 0) AS zadol
        , s.SEGMENT AS afr
        , CASE WHEN a.bin IS NOT NULL THEN 1 ELSE 0 END AS in_b2a
    FROM       [CL_PORTFOLIO].[dbo].[AQR2025_B1A_2024_Q4]            AS b
    INNER JOIN [CL_PORTFOLIO].[dbo].[RA_NST_segment_AQR2025_ot_AFR]  AS s

           ON  a.bin = b.iin_bin
    WHERE b.is_del = '0'
),
v1_agg AS (
    SELECT *, SUM(zadol) OVER (PARTITION BY iin_bin) AS zadol_borrower
    FROM v1_base
)
SELECT *
    /* ---- СТАРЫЕ правила: с ветками флагов и portfolio ---------------- */
    , CASE
        WHEN entity = 'EUB1'                       THEN 'DISASS'

        WHEN zadol_borrower >= @capital * @thr_ind THEN 'Individual loans'
        WHEN (debtor_type_n = 1 OR (debtor_type_n = 0 AND debtor_se_n = 1))
             AND ent_type_n  IN (1,2,3)
             AND loan_obj_n  IN (1,2,3)
             AND loan_purp_n IN (1,2,3,4,5,8)      THEN 'COREST'
        WHEN ent_type_n = 1                        THEN 'CORLAR'
        WHEN ent_type_n = 2                        THEN 'CORMED'
        WHEN ent_type_n = 3                        THEN 'RETSML'
        WHEN COALESCE(debtor_type_n,0) = 0 AND COALESCE(debtor_se_n,0) = 0
             AND ead_n <= 200000000
             AND portfolio IN ('Mortgage')         THEN 'RETEST'
        WHEN COALESCE(debtor_type_n,0) = 0 AND COALESCE(debtor_se_n,0) = 0
             AND ead_n <= 200000000
             AND COALESCE(collateral_n,0) = 1      THEN 'RETCAR'
        WHEN COALESCE(debtor_type_n,0) = 0 AND COALESCE(debtor_se_n,0) = 0

        ELSE 'X'

    /* ---- НОВЫЕ правила: без веток флагов, розница по loan_obj --------

        WHEN (debtor_type_n = 1 OR (debtor_type_n = 0 AND debtor_se_n = 1))
             AND ent_type_n  IN (1,2,3)
             AND loan_obj_n  IN (1,2,3)
             AND loan_purp_n IN (1,2,3,4,5,8)      THEN 'COREST'
        WHEN ent_type_n = 1                        THEN 'CORLAR'
        WHEN ent_type_n = 2                        THEN 'CORMED'
        WHEN ent_type_n = 3                        THEN 'RETSML'
        WHEN COALESCE(debtor_type_n,0) = 0 AND COALESCE(debtor_se_n,0) = 0
             AND ead_n <= 200000000

                 WHEN loan_obj_n = 1               THEN 'RETEST'
                 WHEN COALESCE(collateral_n,0) = 1 THEN 'RETCAR'
                 ELSE                                   'RETCON'
               END
        ELSE 'X'
      END AS seg_new
INTO #nst_v1
FROM v1_agg
OPTION (MAXDOP 1);

     , SUM(CASE WHEN seg_new = afr THEN 1 ELSE 0 END) AS hit_new
     , ROUND(100.0*SUM(CASE WHEN seg_old = afr THEN 1 ELSE 0 END)/COUNT(*), 3) AS acc_old_pct
     , ROUND(100.0*SUM(CASE WHEN seg_new = afr THEN 1 ELSE 0 END)/COUNT(*), 3) AS acc_new_pct

             / NULLIF(SUM(ead_n),0), 2) AS acc_new_ead_pct
FROM #nst_v1;

-- 1.2. Что осталось неверным у новых правил

-- 1.4. Проверка розничной правки: стало ли лучше в RETEST

     , SUM(CASE WHEN seg_old = 'RETEST' AND afr = 'RETEST' THEN 1 ELSE 0 END) AS verno
FROM #nst_v1
UNION ALL
SELECT 'RETEST новое правило'

ORDER BY contracts DESC;

DROP TABLE #nst_v1;
```

    FROM b1a

    , CASE WHEN stage_b = '4'             THEN '3'
           WHEN stage_b = '1111111111111' THEN '1'

   Только после него можно что-то решать по Р1, Р2, Р3.

# Разбор действующих скриптов сегментации и расчёта метрик

Два скрипта: сегментация (`segment_afr` для B1A и B1B) и расчёт средневзвешенных
риск-метрик по (сегмент × стадия). Замечания упорядочены по влиянию на результат;
номера 12 и 13 добавлены позже разбора Инструкции к шаблону и стоят по месту
влияния, а не в конце. Обновлено 21.08.2026.

## Критично: искажает значения метрик

### 1. Обнуление заглушек занижает средневзвешенные — ОТОЗВАНО 21.08.2026

> **Отзыв находки.** Замечание было заявлено как критичное. Прогон Q2 и Q3
> его не подтверждает: договоры с заглушкой `lgd`, `pd_c12`, `pd_cl` несут
> **нулевой EAD**, поэтому доля веса заглушек равна 0,00 % во всех 27 парах
> (сегмент × стадия), а `lgd_now` и `lgd_fixed` совпадают до последнего знака.
> Влияние правки на сегодняшних данных — **ровно ноль**.
>
> Механизм искажения ниже описан верно, но величина не проверялась перед тем,
> как отнести замечание к критичным. Приоритет снижен до гигиены: правку стоит
> сделать (дёшево, защищает при изменении данных), исправлением ошибки она
> не является.
>
> **Существенно другое:** заглушки весят только у `pd_ol` — 5,47 % веса
> на 1 221 договоре. Это ровно та метрика, для которой средневзвешенная
> не считается вовсе (замечание 2). Подробности — `CHECKS_RESULTS.md`, 2.1.

Исходная формулировка сохранена ниже без изменений.

```sql
CASE WHEN gg.lgd IN ('1111111111111','9999999999999') THEN 0 ELSE CAST(gg.lgd AS FLOAT) END AS lgd_new
...
ISNULL(d.lgd_new * d.ead / NULLIF(a.ead_total, 0), 0) AS lgd_sred
```

Заглушка означает «значение отсутствует», а не «значение равно нулю». Сейчас такой
заём входит в знаменатель `ead_total` со своим EAD, но добавляет в числитель ноль —
средневзвешенная метрика по сегменту занижается пропорционально доле заглушек.

**Предложение.** Исключать заглушки из обеих частей: считать веса только по займам
с известной метрикой.

```sql
-- вес и вклад считаются на одном и том же множестве
SUM(CASE WHEN lgd_new IS NOT NULL THEN ead END) OVER (PARTITION BY segment_afr, stage_b_new) AS ead_lgd_base
```

И обязательно выводить долю заглушек по каждому (сегмент × стадия) — это одновременно
метрика заполняемости, за которую отвечает БРМ.

### 2. Отсутствует средневзвешенная по `pd_ol`

`pd_ol_new` вычисляется, но `pd_ol_sred` не считается — в отличие от `pd_c12_sred`
и `pd_cl_sred`. Либо поле не нужно (тогда убрать из расчёта), либо нужно (тогда
добавить), но асимметрия не должна оставаться незамеченной.

### 2а (замечание 12). LGD взвешивается только по EAD

Добавлено 21.08.2026 после разбора Инструкции к шаблону НСТ.

```sql
ISNULL(d.lgd_new * d.ead / NULLIF(a.ead_total, 0), 0) AS lgd_sred
```

Вес — EAD. Инструкция требует другого: LGD — «средневзвешенное по сумме
задолженности под риском (EAD) **и вероятности перехода из стадии**» (Таблица 2),
а в стресс-тесте дословно — «средневзвешенное по сумме задолженности под риском
(EAD) **и вероятности перехода из стадии 1 в стадию 3 в течение квартала**»
(LGD¹⁻³), аналогично для LGD²⁻³.

Смысл: усреднять LGD нужно по той части портфеля, которая **уйдёт в дефолт**,
а не по всему портфелю. Заём с большим EAD и низкой вероятностью перехода сейчас
тянет средневзвешенную на себя сильнее, чем должен.

**Предложение.** Вес `ead × pd_perehod`, где вероятность перехода берётся
для соответствующей пары стадий:

```sql
-- концептуально; конкретное поле вероятности зависит от того, что решим по О2
SUM(lgd_new * ead * tr_out) OVER (PARTITION BY segment_afr, stage_b_new)
  / NULLIF(SUM(ead * tr_out) OVER (PARTITION BY segment_afr, stage_b_new), 0) AS lgd_sred
```

Правка меняет значения по всем сегментам и стадиям, поэтому до её внесения
наши цифры несопоставимы с тем, что ждёт шаблон.

### 2б (замечание 14). `LSBOO = 1` роняет запрос при заглушке

Добавлено 21.08.2026 после ответа смежников.

```sql
when LSBOO = 1 then 'RELATE'
```

`lsboo` — `nvarchar(13)`, и ширина не случайна: `'1111111111111'` — ровно
13 символов. Смежники подтвердили, что на промежуточные даты для юрлиц
эта заглушка допускается.

Сравнение `nvarchar` с числовым литералом заставляет SQL Server приводить строку
к `int`. `1111111111111` превышает диапазон `int` (2 147 483 647), поэтому
результат — **аварийная остановка всей инструкции** по переполнению, а не пропуск
строки. Сегодня расчёт проходит только потому, что в этом срезе заглушек нет.

**Предложение.** Везде, где сравнение идёт с текстовым полем, приводить явно
и безопасно:

```sql
when TRY_CAST(lsboo AS float) = 1 then 'RELATE'
```

То же относится к `ent_type` со значением `9999999999999` («данных нет»):
`cast(... as float)` его переживает, неявное приведение к `int` — нет.

### 3. Несопоставленные сегменты исчезают молча — ЗАКРЫТО 21.08.2026

> **Проверено (Q4).** B1A: 731 159 строк, `NULL` — 0, `X` — 0. B1B: 240 строк,
> так же по нулям. Ветка `else 'X'` не срабатывает ни разу, все договоры
> классифицированы. Исправлять нечего; контрольный запрос ниже стоит оставить
> как регулярную проверку перед каждым расчётом.

```sql
LEFT JOIN [personal_tables].[dbo].[RA_NST_segment_AQR2025] fg ON gg.loan_id_kr = fg.loan_id_kr
```

При отсутствии соответствия `segment_afr` равен `NULL`, и такие займы попадают
в группу `NULL` при агрегации — без предупреждения. В фактической выгрузке
сегментации кода `X` нет вовсе, что подозрительно (см. `SEGMENTS.md`, находка 3).

**Предложение.** Контрольный запрос перед расчётом:

```sql
SELECT COUNT(*) AS rows_total,
       SUM(CASE WHEN segment_afr IS NULL THEN 1 ELSE 0 END) AS no_segment,
       SUM(CASE WHEN segment_afr = 'X'  THEN 1 ELSE 0 END) AS segment_x
FROM ...;
```

Расчёт не запускается, пока `no_segment + segment_x` не объяснены.

## Существенно: влияет на состав сегментов

### 4. Порядок ветвления: `ENT_TYPE` проверяется раньше признаков розницы

Шаги 7 и 8–10 в `CASE`: `ENT_TYPE in (1,2,3)` срабатывает **до** проверки
`DEBTOR_TYPE = 0` (физическое лицо). Если у розничного займа заполнен `ENT_TYPE`
(что не исключено при выгрузке из разных систем), он уйдёт в `CORLAR`, `CORMED`
или `RETSML` вместо `RETEST`/`RETCAR`/`RETCON`.

**Проверка на данных** (одна строка, до расчёта):

```sql
SELECT ent_type, COUNT(*) FROM ... WHERE debtor_type = 0 AND ent_type IN (1,2,3) GROUP BY ent_type;
```

Если результат не пуст — порядок ветвления нужно менять: сначала отделять ФЛ.

> **Проверено, и справочник ужесточает вывод.** Результат не пуст: 1 246 договоров.
> Из них 1 206 — ИП и КХ (`debtor_se = 1`), они уходят в предпринимательские
> сегменты **по замыслу** (розничные ветки требуют `debtor_se = 0`), и это
> подтверждено смежниками. Остаются **40 договоров** физлиц-не-ИП с `ent_type = 3`.
> Справочник АФР содержит для `ENT_TYPE` только значения `1`, `2`, `3` —
> категорию субъекта предпринимательства, которой у обычного физлица быть
> не должно. Значит это **дефект данных**, а не только порядка ветвления:
> менять порядок нужно, но параллельно чинить источник.

### 5. Индивидуальные займы и ОУСА не перераспределяются

По Таблице 3 Методруководства эти два портфеля для кредитного риска
«распределены по другим портфелям». В скрипте они остаются самостоятельными
значениями `segment_afr`. Нужен отдельный шаг: сохранять **продуктовый** сегмент
займа рядом с признаком «индивидуальный / ОУСА», чтобы для кредитного риска
считать по продуктовому, а для ЧПД — по портфелю AQR.

**Предложение.** Две колонки вместо одной: `segment_aqr` (как сейчас)
и `segment_nst_credit` (продуктовый, без DISASS и Individual loans).

### 6. Порог индивидуальной значимости зашит числом — влияние не подтвердилось

> **Проверено (Q8).** По зашитому капиталу на 01.01.2025 и по текущему капиталу
> получается **один и тот же** состав: 67 заёмщиков, одинаковая сумма.
> Предположение, что устаревший порог молча меняет периметр индивидуальных

```sql
>= 461235157000 * 0.002   -- капитал на 01.01.2025
```

При смене отчётной даты порог молча остаётся прошлогодним.

**Предложение.** Вынести в параметр (переменная, таблица параметров или CTE
с одной строкой) и указывать дату капитала рядом со значением.

### 7. `RETEST` определяется по `portfolio = 'Mortgage'`, признак залога отключён

```sql
--    and coalesce(cast(collateral as float), 0) = 1
    and portfolio in ('Mortgage') then 'RETEST'
```

Портфель НСТ называется «Займы физических лиц, обеспеченные жилой недвижимостью»,
то есть определяющим является обеспечение, а не метка продукта. Сейчас классификация
опирается на `portfolio`, а проверка залога закомментирована.

> **Решение найдено 21.08.2026.** Возвращать закомментированное условие
> бессмысленно: `collateral` — бинарный факт наличия залога, вида залога он
> не содержит в принципе. Вид залога лежит в **форме B2D**. Значит `RETEST`
> строится присоединением B2D по договору и отбором жилой недвижимости,
> а не спором о том, эквивалентна ли метка `Mortgage` обеспечению.
> По данным это затрагивает 49 договоров — 9,4 % EAD сегмента.

### 8. `RETCAR` = «обеспеченные», но без различения вида обеспечения

Шаг 9 относит к `RETCAR` любой обеспеченный заём ФЛ (`collateral = 1`), тогда как
портфель называется «Автокредиты и прочие обеспеченные займы». Формально совпадает
с названием, но стоит зафиксировать в пояснительной записке, что автокредиты
и прочие обеспеченные не разделяются.

## Методологически: требует фиксации

### 9. База задолженности в B1A и B1B считается по-разному

- B1A: `od + od_del + interest + interest_del + correction + disc_prem + penalty`
- B1B: `correction + disc_prem + penalty`

Для кредитных линий (B1B) отсутствие основного долга объяснимо, но это должно быть
описано явно — иначе при сверке сумм расхождение выглядит как ошибка. Кроме того,
включение `penalty` не следует из определения задолженности в п. 44 Методруководства
(см. `GLOSSARY.md`, открытый вопрос 1).

### 10. Приведение стадий фиксируется как допущение

`stage_b = 4 → 3` и `stage_b = '1111111111111' → 1`. Второе особенно чувствительно:
заглушка трактуется как отсутствие обесценения. Нужно посчитать, сколько таких
записей и на какую сумму, и указать это в пояснительной записке.

```sql
SELECT stage_b, COUNT(*) n, SUM(CAST(ead AS FLOAT))/1e9 ead_mlrd
FROM ... GROUP BY stage_b ORDER BY n DESC;
```

### 10а (замечание 13). Оставшийся срок стадии 2 — месяцы против лет

В выгрузке результатов AQR-2025 колонка «Оставшийся срок погашения (для займов
в стадии 2)» имеет в шапке единицу **«Месяцы»**. Шаблон НСТ требует «количество
**лет** до погашения… округляется до десятых долей года». Перенос значения
без деления на 12 завышает срок в двенадцать раз и, через PD lifetime, завышает LRLT.

Единица подтверждается величинами: ипотека 86,07, автокредиты 58,88,
потребительские 38,27 — как годы это невозможно, как месяцы даёт 7,2 / 4,9 / 3,2 года.

Отдельно: по портфелю «Индивидуальные займы» срок стадии 2 равен **нулю**
при задолженности стадии 2 в 15,8 млрд ₸. Это пропуск, а не отсутствие стадии 2;
нужен контроль «срок = 0 при задолженности стадии 2 > 0».

Правки тривиальные, но должны быть явной строкой с комментарием, а не молча.

### 11. Агрегат считается по факту, а не по периметру НСТ

`AGG` группирует всё, что прошло фильтр `is_del = '0'`. Портфели, которые
по Таблице 3 в кредитном риске **не анализируются** (займы финансовым институтам,
государственным структурам, дебиторская задолженность), должны исключаться
из расчёта метрик кредитного риска — иначе средневзвешенные считаются по более
широкому множеству, чем требуется.

> **Стало проверяемым 21.08.2026.** Справочник АФР по `LOAN_TYPE` даёт периметр
> инструментов: `1` заём, `2` кредитная карта — займы; `3` гарантия,
> `4` аккредитив, `9` возможные обязательства по векселям, `10` условные
> требования — условные и возможные обязательства; `5` финансовый лизинг,
> `6` факторинг, `7` форфейтинг, `8` вексель — не займы в узком смысле.
> Таблица 3 оперирует займами. В сегментации поле `loan_type` **не используется
> ни разу**, поэтому первый шаг — распределение по нему: оно покажет, сколько
> незаймовых инструментов сидит в расчёте кредитного риска.

# Провизии по продуктам CrediLogic и Fenix: логика расчёта в рабочих книгах

Заведён 01.10.2026. Предмет — как УКРР считает провизии МСФО 9 по розничным продуктам,
которые живут в источниках **CrediLogic (S03)** и **Fenix (S17)**: CAR, DSL Online, Loyalty,
PayRoll, UnCL и POS + FENIX. Карточные продукты источника **S02** (Payda, SmartCard, КП,
КПК, Installment) сюда не входят — у них другая структура книг (§ 5).

Основа — формулы рабочих книг за август 2026 года, снятые ноутбуком локально у автора
(`formula_patterns.csv`, `inventory.md`). Книги в репозиторий не кладутся (корневой
`CLAUDE.md` § 2): в листах `Base` — номера договоров, в списках умерших — ИИН. Здесь только
формулы, адреса ячеек и агрегаты. Значения есть только по CAR — они в
[`AUTO_PD_LGD.md`](AUTO_PD_LGD.md) § 7.

---

## 0. Сначала возражение: «по продуктам» — это не шесть разных методов

Все шесть книг собраны **из одного шаблона**. Различаются ячейки, из которых берутся PD,
LGD и макрофактор, и одна деталь стадии 3 (залог у CAR). Поэтому вопрос «как считается
провизия по продукту» на деле распадается на два:

1. как устроен шаблон (§ 2) — он один;
2. откуда шаблон получает три числа (§ 3) — здесь и прячутся различия, и именно здесь
   найдены совпадения, которых быть не должно (§ 4).

Сопоставление продукта с источником — **гипотеза Г-CLF-1** для CrediLogic: по префиксам
номеров договоров в формулах (`L211…`, `CL21`) и по имени листа прогноза
`2-3_корз_CL_Fenix`. Состав S02 (Payda, SmartCard, Installment, КПК) доказан в
`risk_dwh_reconciliation/FINDINGS.md`; S17 = Fenix — там же.

## 2. Шаблон — общий для всех шести

### 2.1 Входы книги

| Вход | Что это | Как попадает |
|---|---|---|
| `Корзина 3` | список договоров в дефолте: дата дефолта, EAD в дефолте, причина. Общий для всех продуктов (610 762 строки) | вставка |
| `Корзина 2` | список договоров стадии 2 с корзиной | вставка |
| `POCI` | купленные / созданные обесцененными | вставка |
| `Умершие 100% (СЗ)` | умершие заёмщики — провизия 100 % | вставка |
| `Реструктуризации` | реструктуризации с датой | вставка |
| `Корзина на <прошлая дата>` | стадия на прошлую отчётную дату | вставка |
| `Справочник` | префикс договора → подпродукт | вставка |
| PD-, LGD-книги, книга макрокорректировки | три числа и кривая возврата (§ 3) | внешние ссылки |

### 2.2 Лист `Base` — по договору

    R  корзина  = месяц дефолта из «Корзина 3»
                  иначе из POCI
                  иначе корзина из «Корзина 2»
                  иначе по DPD: < 30 → "0-29", иначе "30-90"
    T  стадия   = POCI / умерший (из своих списков)
                  иначе "0-29" → 1, "30-90" → 2, остальное → 3
    S  EAD в дефолте (из «Корзина 3» / POCI), иначе 0
    N + O + P   = портфель (ОД + % с дисконтом/премией) + штрафы + комиссии
    V  ожидаемый возврат стадии 3 = MIN(N + O + P; S) × F(R)
    X  ставка провизии по стадии ← «% МСФО 9»;   Y = X × N

### 2.3 Лист продукта — расчёт

| Шаг | Формула (CAR; у остальных та же со своими адресами) |
|---|---|
| PD с макрофактором | `C7 = E7 · (1 + D7)` — PD 12 мес.; строка 8 — то же для PD на весь срок |
| Стадия 1 | `H16 = E16 · C9 · C7` — баланс корзины `"0-29"` × LGD × PD 12 мес. |
| Стадия 2 | та же формула в строке 17 — баланс `"30-90"` × LGD × PD на весь срок (строка 8). Что берётся PD на весь срок, подтверждает B1A: провизия стадии 2 банка ≈ EAD × LGD × PD LT |
| Стадия 3, поколение дефолта `m` | `D` = EAD в дефолте, `E` = баланс, `G` = ΣV, `H = MAX(E − G; 0)` |
| Коэффициент ожидаемого возврата | `F_m = Σ_{t ≥ m} K_t` — остаток кривой возврата от возраста поколения до конца; у CAR плюс `L_m` = TV/EAD поколения |
| Сверка | строка «итого»: `SUMIF(Base…) − SUM(по поколениям)` — остаток должен быть 0 |

### 2.4 Лист `% МСФО 9` — сборка по стадиям

`SUMIFS` по `Base` в разрезе стадии `T`, отдельно без умерших и только умершие. Ставка
стадии = провизия / портфель; она возвращается в `Base!X` и умножается на портфель
договора. Это и есть загружаемая в АБС величина.

## 3. Откуда шаблон берёт три числа — по продуктам

| Продукт | PD | LGD | Макрофактор: файл, строка | Кривая для стадии 3 | Отличия |
|---|---|---|---|---|---|
| **CAR** | `Result_201207!F174` | `LGD_results!D168` (с вычетом залога) | 2026, **R73** | `TVp!C3…` + `L` (TV/EAD) | единственный с залогом; NCL / UCL по жёсткому списку префиксов |
| **DSL Online** | `F176` | `LGD_results!C179` | 2026, **R2973** | `For provisions!C3…`, до строки 57 | в таблице стадии 3 — 57 поколений дефолта против ~160 у остальных |

## 4. Находки

| Код | Находка | Основание | Статус |
|---|---|---|---|
| **И-16** | **DSL и PayRoll получают макрофактор из одной строки** (`R2973`) книги макрокорректировки 2026 года. Либо это осознанная общая модель для двух беззалоговых продуктов, либо PayRoll скопирован с DSL без замены строки | `DslOnline!D7`, `PayRoll_provisions!D7` | доказано формулой; намерение — вопрос В-CLF-1 |
| **И-17** | **UnCL берёт макрофактор из файла 2025 года** (`Макрокорректировка 2025/…_с фильтром`), остальные пять — из 2026 года | внешние связи книги UnCL | доказано; фактическое значение — по выгрузке |
| **И-18** | **Коэффициент ожидаемого возврата `F` не ограничен единицей.** У карточных Payda и SmartCard ограничение 100 % есть (`RR!C4`), у шести продуктов CL / Fenix — нет. **При текущих кривых `F < 1`:** у CAR максимум 0,37 (возврат за 23 мес.) + 0,44 (TV/EAD) = 0,81. Риск латентный — сработает, если кривая или TV вырастут | `CAR!F18`, `DslOnline!F18` и др.; `Payda RR!C4` | доказано формулой; у CAR на значениях `F ≤ 0,81` |
| **И-19** | **LGD шаблона берётся из разных ячеек:** `D168` у CAR (подписана «LGD+TV_DISCOUNTED»), `C179` у остальных. Структура LGD-книг различается; что лежит в `C179` — LGD с вычетом залога или без, — по этим книгам не видно | `C9` листов продуктов | доказано; содержание `C179` — по выгрузке LGD-книг |
| **И-20** | **POS и FENIX считаются одной кривой и одним PD**, хотя это разные источники (S03 и S17) с разной историей. Отдельной провизии FENIX в книге нет | `POS_provisions!E16`, `G18`, `D18` — суммы по `$C$4` и `$C$5` | доказано формулой |
| **И-21** | **Стадия 3 у всех шести — только по внешнему списку** `Корзина 3` (И-2 для CAR верна для всего шаблона): договор с DPD ≥ 91 вне списка получает корзину `"30-90"` и стадию 2 | `Base!R4`, `T4` — общий шаблон | доказано формулой |
| **И-22** | **ER стадии 3 считается от `MIN(баланс; EAD)`, а не от EAD** (И-1 для CAR) — во всех шести книгах | `Base!V4`, общий шаблон | доказано формулой; эффект не измерен |

## 5. Почему карточные продукты S02 вне этого документа

| Продукт | Чем отличается |
|---|---|
| Payda, SmartCard | своя структура `Base` (столбцы E/F/G/H); PD из книги **на 27.03.2026**; LGD — **у POS + FENIX**; макрофактор — строка `R5392` файла **2025** года, общая для обоих; кривая возврата ограничена 100 % |
| Card (КП) | ожидаемый возврат стадии 3 — другой формулой (`(ΣRR + TV) × B`); макрофактор — та же строка `R5392` |
| КПК, Installment | **нет модели**: стадия только по DPD (< 30 / 30–90 / > 90), ставка — из таблицы `VLOOKUP(L; P3:Q23)` |

Это отдельный разбор, если он понадобится.

## 6. Что это значит для воспроизведения на данных DWH

Из реестров репозитория, а не из книг:

| Факт | Откуда | Следствие для провизий CL / Fenix |
|---|---|---|
| **Пайплайн урегулирования (`writeoff`, `collections`, `Offbalance`) не покрывает S17** — домен `source` там только S01 и S03 | `cl_registry/links.csv`, CL-S17-02 | **кривую возврата FENIX из mart не построить**: возвратов после дефолта по Fenix в DWH нет. Та же причина, по которой И-20 нельзя проверить на данных |
| Связь S03 с mart — по номеру договора (`contract_number → l_loan_number`), `l_loan_id` даёт 0 совпадений | CL-S03-01 | ключ для сверки списков `Корзина 3` / `Base` с DWH — номер договора |
| Связь S17 — `contractnumber → la_dog_num + source = S17 + дата` | CL-S17-01 | то же для FENIX, но с датой среза |
| `loan_account` историзована только с 2025-01-01 | `dict_registry/objects.csv` | треугольники PD с 2012 года из mart не восстановить; только из старой базы или архивов |
| У S17 часть закрытых договоров помечена открытыми (289 случаев) | `dict_registry/README.md`, Р-1 | периметр FENIX в `Base` надо сверять со статусом, иначе в провизии попадут закрытые договоры |

Отсюда порядок, если идти от DWH (по § 6 корневого `CLAUDE.md` — это предложение, не
решение):

1. **Разведка:** сверить периметр `Base` каждого продукта с mart по ключам CL-S03-01 /
   CL-S17-01 — сколько договоров совпадает, сколько в книге нет в DWH и наоборот.
2. **Списки стадий:** сверить `Корзина 3` с признаками дефолта в mart (DPD ≥ 91,
   реструктуризация) — это проверка И-21 на данных.
3. **Кривая возврата:** для S03 — из `writeoff` / `collections`; для S17 — источника в
   DWH нет, вопрос к владельцу (В-CLF-3).

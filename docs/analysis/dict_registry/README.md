# Реестр полей `Dictionaries.risk_analytics`

Контур-справочник по **новой ветви** хранилища (mart). Заведён 01.09.2026; разрез изменён
02.09.2026 (решения Р2, Р5).

Отвечает на вопрос: **что представляет собой конкретное поле или таблица в конкретном
источнике и чему его значение равно на самом деле.**

## Чем отличается от соседних контуров

| Контур | Ось | Отвечает на |
|---|---|---|
| `risk_dwh_reconciliation` | источник и вопрос сверки | сходится ли OLD с NEW и почему нет |
| **`dict_registry`** | **поле × источник** | что означает поле и можно ли им пользоваться |
| `cl_registry` | связь OLD ↔ NEW | каким ключом старая база связывается с mart |

`FINDINGS.md` контура сверки — **ground truth и первоисточник**. Здесь ничего не доказывается
заново: строки переносятся с прямой ссылкой на раздел, где факт установлен. Расхождение между
этим реестром и `FINDINGS.md` всегда решается в пользу `FINDINGS.md`.

## Разрез: единица строки — поле × источник

Одно поле в четырёх источниках ведёт себя как четыре разных поля: `payment_deferral` пуст
на 100 % по S02, на 99,7 % по S01, на 27 % по S17 и заполнен по S03. Одна строка на поле
это скрывает — поэтому строкой является пара **(поле, источник)**. Значение `все` в колонке
источника держит одну строку там, где разницы нет или она не измерялась.

Отклонённые разрезы: «сущность предметной области → где лежит» (BCBS 239 принцип 2,
таксономия данных) — заводится **индексом поверх** этого реестра, когда полей станет больше
~30; сейчас 18. «Вопрос пригодности» (можно ли посчитать X) — это FAQ, а не реестр.

Источники: **S01** — RS (retail core), **S02** — Cards {Way4, SMARTCARD, Installment, kpk,
Payda}, **S03** — CrediLogic (основная выдача), **S17** — Fenix. Различаются колонкой
`la_source` / `l_source`.

## Состав

| Файл | Что | Единица строки |
|---|---|---|
| `fields.csv` | Поля: таблица, поле, источник, вердикт, число, следствие, откуда | поле × источник |
| `objects.csv` | Таблицы: ключи, историзация, зерно, представления | факт об объекте × источник |
| `DICT_A_schema_audit.sql` | Живой аудит схемы — источник имён | — |

Формат CSV с разделителем `;` и строками-комментариями `#` — как в `risk_showcase/registry/`.
Выбран потому, что строки сюда приходят из выхода `DICT_A` после прогона, и переформатировать
табличный результат в markdown каждый раз — лишняя работа. Внутри полей `;` не используется.
Искусственный идентификатор не нужен: естественный ключ — `таблица.поле@источник`.

## Как читать вердикт

- **непригодно** — поле пустое или содержит не то, что заявлено названием;
- **ловушка** — поле заполнено, но прямая трактовка даёт систематически неверный ответ,
  и в колонке `number` указан масштаб ошибки;
- **пригодно** — проверено и годится, с оговоркой в `consequence`;
- поля, по которым ничего не сказано, **не считаются проверенными**. Их отсутствие здесь
  означает, что их не смотрели, а не что с ними всё в порядке.

## Железное правило пополнения

Раздел 4 корневого CLAUDE.md: **имена колонок берутся только из живого аудита
`INFORMATION_SCHEMA`, не из BI-канваса и не из памяти. Имя колонки ≠ семантика.**

Отсюда три следствия, которые нарушать нельзя:

1. **Ни одна строка не добавляется по названию поля.** Пока поле не встретилось в выгрузке
   схемы и его значения не посчитаны, его здесь нет.
2. **Семантика фиксируется только вместе с числом.** «Поле пустое» без доли заполнения —
   не факт, а впечатление.
3. **Колонка `table` заполняется из первоисточника или из `FROM` запущенных скриптов**, не по
   префиксу имени. Где таблица не названа — прочерк до аудита `DICT_A`; такие строки помечены
   в комментарии файла.

Скрипт `DICT_A_schema_audit.sql` собирает инвентарь схемы. Он read-only, без PII, с MAXDOP 1
и трёхчастными именами — правила раздела 4.
